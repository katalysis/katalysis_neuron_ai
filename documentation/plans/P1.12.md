### 1.2 User entities with no user row (item 2)

### 1.4 The `usersignups` foreign key (item 4)
- `RegistrationService::create()` ([RegistrationService.php](../../../../concrete/src/User/RegistrationService.php) lines 160 to 165) builds `new UserSignup($user, ...)` and never sets `User::$signup`, so the user's in-memory `signup` stays `null`.
- `UserInfo::delete()` relies on the `cascade={"remove"}` of that property (`Entity/User/User.php` line 35), so in the same process nothing removes the sign-up and `DELETE FROM Users` fails on `FK_FEB5D909FD71026C`.
- Probe in a rolled-back transaction (nothing kept):

| Variant | Result |
|---|---|
| create, delete | foreign key error |
| create, join a group, delete | works (joining a group loads `signup`) |
| create, clear the entity manager, reload the user, delete | works |
| create, clear the entity manager, delete the stale object | "Detached entity cannot be removed" |

- In the working variants `UserInfo::delete()` removes the sign-up, its notification and the alerts completely (counts identical before and after).
- The workaround in `TaskKeyFixture::restore()` deletes `UserSignupNotifications` and `UserSignups` by SQL but not the parent `Notifications` and `NotificationAlerts` rows. It leaves 2 notifications and 4 alerts per run: 45 dangling `usersignupnotification` rows with 90 alerts now, the earliest from 20 October 11:10.

## 2. Work, in this order

### 2.1 Fix the tests (test-first)
Rule: tests restore the state they found (CLAUDE.md, Testing).
1. **A shared cleanup helper** `tests/Support/PermissionCleanup.php`: `deleteAccess()` (moved out of `TaskKeyFixture`) and `deleteAreaAssignments(cID)`.
2. **`TaskKeyFixture`.** Test first: `TaskKeyFixtureTest` creates a user, adds it to a group, grants and restores, and compares row counts (Users, UserSignups, UserSignupNotifications, Notifications, NotificationAlerts, the permission tables). It is red today (Notifications +2, NotificationAlerts +4). The fix: `createUser()` clears the entity manager and reloads the user through `UserInfoRepository::getByID`, so `UserInfo::delete()` does the whole job. The SQL workaround is deleted.
3. **`DraftIsolationTest`.** Test first: a case in a new `AreaGrantFixtureTest` that grants, deletes the page and restores, and checks the counts (red against a fixture that only deletes the page). The fix: `allowEditorToAddBlocksToMain` moves into `tests/Support/AreaGrantFixture.php`, which records the access it duplicates; `tearDown()` deletes the area's assignment rows, then the recorded access when no assignment still uses it, then the page. It never touches an access that was already shared.

### 2.2 Permanent leak check
- `tests/Support/DatabaseSnapshot.php`: the exact row count of every base table (one query), and `CHECKSUM TABLE` for a short list (`Config` and the permission, assignment and entity tables), so a restored but altered row is caught too.
- `ConcreteTestCase::setUpBeforeClass()` takes the snapshot after booting; `tearDownAfterClass()` compares and fails, naming the class, the tables and the deltas. **The only allowlisted table is `Logs`.** Anything else needs a stated reason in the constant.
- Tests: a unit test for the comparison and its message (no Concrete); an integration test that inserts a row in a transaction, sees it detected, and rolls back.

### 2.3 One-off cleanup of the existing leftovers
Script: `documentation/fixtures/cleanup_test_leftovers.php`, run with `c5:exec`. It is committed. It needs:
- the seed's dev-host guard (canonical URL `.test`, `.localhost` or `localhost`);
- **a dry run by default.** Nothing changes without `--apply`;
- **row selection by criteria, not hard-coded counts** (below). It prints each criterion with the evidence for it, the counts it found, and anything it did not select;
- `--apply` also needs `--expect=<summary file>` (written by the dry run) and `--dump=<file>` (a fresh dump that exists, is newer than the summary and ends with "Dump completed"). Inside one transaction it selects again and **aborts and rolls back if the numbers differ from the dry run**.

Criteria (all must hold):
1. **Dead-page permission rows.** A candidate page is a `cID` in `AreaPermissionAssignments` that is not in `Collections`, whose rows are exactly the override signature (only `Main`, and every area key once), and that is higher than every live page outside `/neuron-test` (so it was made after the dev site's real content). A page that fails one test is listed, not selected. Selected: its `AreaPermissionAssignments` rows. An access is deleted (with its `PermissionAccessList` rows and its access-list child rows) only if no row in **any** table with a `paID` column, found from `information_schema`, refers to it outside the selected rows. Shared accesses stay.
2. **User entities with no user.** Type user, no `PermissionAccessEntityUsers` row, and no row in any table with a `peID` column (found from `information_schema`), after step 1.
3. **Dangling sign-up notifications.** `Notifications` of type `usersignupnotification` with no `UserSignupNotifications` row, and their `NotificationAlerts`. Other types are reported, not touched.
4. **Not touched:** the four orphan blocks, `Logs`, the 9 rows of the live fixture page, the 2 live sign-up notifications and the 2 group notifications, and anything with a live reference.

Sequence: dry run, fresh dump, `--apply` straight after; a second dry run must then find nothing.

## 5. Risks
- **Checksum noise.** `CHECKSUM TABLE` on a table that a test legitimately changes would fail a class. The first run decides the list; a table leaves the list only with a written reason.
- **A test that fails halfway** may still leave rows; the leak check will then fail the class in addition to the test. That is the intent.
- **The cleanup deletes rows.** Dry run first, a fresh dump, one transaction, a count check inside it, and a second dry run afterwards.

## 6. Test plan

## 9. What changed while doing it (20 October)
1. **Fix for the user fixture is a `refresh`, not clear and reload.** `TaskKeyFixture::createUser()` calls `EntityManager::refresh()` on the new user, which loads `User::$signup` so `UserInfo::delete()` cascades. It is shorter than the plan's clear-and-reload and was verified by the five related test files.
2. **Cleanup criterion 1 changed.** "Higher than every live page outside `/neuron-test`" failed on the first dry run: seven empty global-area stacks (cIDs 6879 to 6885) had been added the same afternoon, so no dead page qualified. The cutoff is now the newest page added before a date the operator gives (`--tests-since=2026-10-19`, the date of the first test commit): cID 437. Every dead page is far above it (the lowest is 3468). The date is required, printed, and part of the summary that `--apply` checks. The old reasoning (all dead cIDs are above 376, the highest page made before 12 October) still holds.
3. **A throwaway page of my own was left behind** by the red `AreaGrantFixtureTest` run (cID 7008, `/neuron-test/area-grant-fixture-6acf9d`). I deleted it through Concrete (path-guarded) before the dry run, so its nine rows were then picked up by the cleanup like the rest. The test now deletes its pages and restores its grants in `tearDown()`, so a failed assertion cannot leave them.
4. **Clearing the cache removed seven empty stacks.** Concrete's cache clear deletes empty global-area stacks that a page view auto-creates. The seven (type 20, no blocks in the pre-apply dump) went when the cleanup script cleared the cache, as the seed does on every run. Nothing of value was lost; they come back when a page with those global areas is next viewed.
5. **The cleanup logic lives in `tests/Support/LeftoverCleanup.php`** and the script in `documentation/fixtures/` is the command line around it, so the selection is tested (`LeftoverCleanupTest`, 10 tests, on a throwaway fixture inside a rolled-back transaction).
6. **CHECKSUM TABLE returns lower-case table names** on this server; `DatabaseSnapshot` maps them back.
