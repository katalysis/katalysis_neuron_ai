## 2. What Neuron 4 can observe or send out (checked 2026-10-22, before any edit)

### 2.1 The event system
- Every `Workflow` (and so every `Agent`: `Agent extends Workflow`, `src/Agent/Agent.php:60`) owns a PSR-14 dispatcher through the `HandleDispatcher` trait (`src/Workflow/Workflow.php:34`). There is no global or static state (`src/Observability/AGENTS.md:3`).
- **Three ways to attach anything**, all explicit calls on the agent (`src/Workflow/HandleDispatcher.php`):
  - `subscribe(eventClass, listener)` (35–41)
  - `observe(ObserverInterface)`, deprecated, which wraps the observer in `ObserverAdapter` and subscribes it to every event (24–27; `src/Observability/ObserverAdapter.php:21–28`)
  - `setEventDispatcher(PSR-14 dispatcher)`, which forwards every event to a host dispatcher after the agent's own listeners (47–53; `src/Observability/EventDispatcher.php:37–43`)
- **Defaults:** the listener registry starts empty (`Workflow.php:43`, `HandleDispatcher.php:63–66`) and the forward target starts null (`HandleDispatcher.php:18`). Nothing in `vendor/neuron-core/neuron-ai/src` calls `subscribe()`, `observe()` or `setEventDispatcher()` (searched: the only hits are doc comments). The per-run `SegmentEventDispatcher` only stamps the run context and source on each event and passes it on (`src/Workflow/Executor/SegmentEventDispatcher.php:28–35`).
- **So by default every event goes to an empty listener list and stops there.**

### 2.2 What the events carry (if someone attaches a listener)
`toArray()` per event, and the public properties a listener can read:
- `InferenceStart` / `InferenceStop`: the message sent and the reply, in full (`src/Agent/Observability/InferenceStart.php:16–19`, `InferenceStop.php:19–25`), so the user's text, page content and tool results.
- `ToolCalling` / `ToolCalled`: the `ToolCall`, with its inputs and result (`ToolCalled.php:12–19`). Emitted by `ToolNode` (104, 111, 444, 461), `ParallelToolNode` (113, 205) and, for approved deferred calls, `AwaitToolResultsNode` (80).
- `MessageSaving` / `MessageSaved`: every message stored.
- `WorkflowError`: `toArray()` gives only `getMessage()` (`src/Workflow/Observability/WorkflowError.php:23–25`), but the public `$exception` is the exception object. For a provider failure that is an `HttpException` whose public `$request` holds the headers, including `Authorization: Bearer <key>` (`src/Exceptions/HttpException.php:20–21`; `src/Providers/OpenAI/OpenAI.php:61`). Its message holds the URL without user info and the **response body** (`HttpException.php:30`).
- Every event's public `$source` is the emitting node or the agent itself (`src/Observability/ObservabilityEvent.php:25`).

So a listener that dumps event objects, rather than `toArray()`, can log the key; one that logs `toArray()` logs conversation content.

### 2.3 Monitoring integrations, environment variables and config
- **Neuron 4 bundles no monitoring integration.** Its `require` is `php`, `ext-curl` and `psr/event-dispatcher` (`composer.json:12–16`). `psr/log` is only suggested, "for logging observability events through `LogListener`" (`composer.json:97`). Our `vendor/` holds only `neuron-core/neuron-ai` and `psr/event-dispatcher`.
- **No environment variable or config switches anything on.** The only `getenv()` in the source is `MCP/StdioTransport.php:130` (passing `PATH` to a child process for an MCP stdio server); no `$_ENV` or `$_SERVER` read anywhere; no Inspector, OpenTelemetry, Langfuse or other telemetry code.
- **Other outbound paths in v4, none used by us:** streaming channels (Mercure, Pusher, Redis: `src/Workflow/Streaming/Channel/`), MCP transports (`src/MCP/`), embeddings and vector stores (`src/RAG/`). Each needs explicit construction. Our `src/Tools/McpServerIntegration.php` is not referenced anywhere.
- **The one outbound request a turn makes is the provider call**: `OpenAI` posts to `https://api.openai.com/v1/chat/completions` (`OpenAI.php:37, 68`) through `CurlHttpClient` unless a client is passed in (`OpenAI.php:57`). Our `provider()` passes the key and model from `katalysis.ai.*` and nothing else (`src/ConcreteCmsAgent.php:237–243`).

### 2.4 For comparison: Neuron 3, still on `development` and `main`
**v3 attaches Inspector by default.** `EventBus::emit()` observes `InspectorObserver::instance()` for any scope with no observer registered (`vendor/neuron-core/neuron-ai/src/Observability/EventBus.php:72`), and `vendor/inspector-apm/inspector-php` is bundled. `InspectorObserver::instance()` reads `$_ENV['INSPECTOR_INGESTION_KEY']`, `INSPECTOR_TRANSPORT`, `INSPECTOR_MAX_ITEMS`, `INSPECTOR_URL`, `NEURON_SPLIT_MONITORING` and `NEURON_AUTOFLUSH` (`inspector-php/src/Neuron/InspectorObserver.php:111–139`). Transfer is enabled only when an ingestion key is set (`Configuration.php:151`), and then goes to `https://ingest.inspector.dev` (`Configuration.php:20`) with the agent's instructions, its tool list and the messages (`InspectorObserver::getAgentContext()`, `prepareMessageItem()`).
- So on v3, setting `INSPECTOR_INGESTION_KEY` in the PHP environment of a site would send prompts and conversation content to Inspector, with no change to our code. Concrete doesn't load a `.env` file (no dotenv in `concrete/bootstrap` or `concrete/src/Foundation`), so it would take a server or PHP-FPM environment setting.
- **P2.9 removes Inspector:** v4 has no Inspector code and no default observer (2.3), and P2.9 brings v4 to `development`. No other copy of `inspector-apm` is on the dev site (searched the other packages, `concrete/vendor` and `application`).

## 4. `ConcreteCmsLogObserver` on v4: works, but isn't safe
Checked against the v4 source:
- **It loads and would run.** It extends `LogObserver`, which v4 keeps but deprecates for removal in the next major (`src/Observability/LogObserver.php:13–16`). Its constructor skips the parent's, so the parent's `readonly $logger` stays unset; that is harmless only because it overrides `onEvent()` and never touches `$logger`.
- **What it would log on v4 is wrong and unsafe.** Through `observe()`, `ObserverAdapter` passes the **event object** as `$data`. The observer's own `serializeObject()` then puts every public property in the log context:
  - `source`: the node or the whole agent object
  - `exception` on `WorkflowError`: the `HttpException`, whose `request` holds the `Authorization` header
  - `message`, `tool`: conversation content as objects

  Whether the key reaches the `Logs` table then depends on how Concrete's Monolog formatter serialises objects in the context. It must not depend on that (B-SEC-1). Nothing goes through `SecretRedactor`.

**Proposed fix (decision D1), small and still not attached:**
- Keep the class and its name; keep `LogObserver` as the base, so it can still be passed to `observe()` until Phase 3 replaces it with a `LogListener` subscription.
- The constructor calls the parent with Concrete's PSR-3 application logger (resolved from the container; a logger can be passed in, for tests) and the level.
- Remove the overrides of `onEvent()`, `serializeData()` and `serializeObject()` (about 45 lines). The parent's `onEvent()` then logs the event's `name()` with `context($event)`, and for a non-event `$data` an array or nothing (`LogObserver.php:20–39`).
- Override `context()`: take the event's `toArray()` only (never its public properties), replace any object left in it with its class name, and pass every string, at any depth, through `SecretRedactor::redact()`.

Result: no exception, request, source or agent object can reach a log, and the configured keys are redacted wherever they appear, including in a provider's response body quoted in a `WorkflowError` message.

**Alternative (D1b):** delete the file. It is unused and its base class goes in Neuron 5. Phase 3's PSR-14 listener would be written from scratch. I recommend D1a, because the DELIVERY_PLAN asks for the observer to work, and the redacting `context()` is exactly what Phase 3's `LogListener` subclass will need (`LogListener::context()` is the same hook, `src/Observability/LogListener.php:38–41`).

Still not attached, either way. Attaching a log of conversation content is a retention question (B: chat history 90 days; `Logs` has its own retention), so it waits for Phase 3 and Glyn.

## 5. Audit logging: which tools ran in a turn (for P3.6)
**Recommendation: P3.6 should use a listener on `ToolCalling` / `ToolCalled`, held by the agent.** Don't build it in P2.7.
- **Why an event listener fits:**
  - `ToolCalled` fires once per settled call, with the call's name, inputs and result, from every path: sequential, parallel, and **deferred calls approved later** (`AwaitToolResultsNode.php:80`). That last path is the one P3.6's approval flow creates, and our own tool wrapper can't see when an approved call settles in a later request.
  - The listener is an object the agent holds, so its record **survives a failed turn**. In P2.6 the failed run's state couldn't be reached after the exception; a listener's record can be read in `handle()`'s `catch`, which is what naming "the write tools that ran before a failed turn" needs.
  - One agent per request (P2.6) gives one record per turn with no reset logic.
- **Limits P3.6 must design for:**
  - Neuron says the events "describe execution and are not a durable audit log; retries after an uncommitted step may emit them again" (`src/Observability/AGENTS.md:28`). So: de-duplicate by tool call ID, and write the durable record ourselves (our own table, at the end of the turn and in the error path), not from inside the listener.
  - Whether a call wrote something is decided by `ToolKind` (write or read) and our `{ok, …}` envelope in the result, not by the event.
  - What is recorded goes through `SecretRedactor`, as in §4.
- **Why not now:** it's small (a listener class and a test), but nothing would use it until P3.6 changes the error reply, and that is a behaviour change with scenarios. Built now, it would be unused code to keep in step with P3.6's design.

## 6. Tests

### 6.1 New: `tests/Integration/OutboundDataTest.php`
Proves that nothing sends conversation data, prompts or keys off the site unless we configure it. No AI provider call, no key: a dummy key string and a recording HTTP client. Leak-checked like every `ConcreteTestCase`; it stores no chat.
1. **No listener and no forwarding by default:** a `ConcreteCmsAgent` (as the controller and the runner build it), after a full turn (`FakeAIProvider`, one tool call then a reply), has an empty listener registry and no external dispatcher (read by reflection: `listeners`, `externalDispatcher`).
2. **Monitoring environment variables change nothing:** the same, with `INSPECTOR_INGESTION_KEY`, `INSPECTOR_URL`, `INSPECTOR_TRANSPORT`, `NEURON_SPLIT_MONITORING` and `NEURON_AUTOFLUSH` set in `$_ENV` and `putenv()` before the agent is built (restored after). Also: no `Inspector\` class is declared after the turn.
3. **The only requests a turn makes are to the provider:** the agent's `provider()` overridden to return Neuron's real `OpenAI` provider with a dummy key and a recording `HttpClientInterface` that answers with canned chat-completion JSON (one tool call, then a reply). Asserts: exactly 2 requests, both `POST https://api.openai.com/v1/chat/completions`, nothing else.

### 6.2 New: `tests/Unit/BundledDependenciesTest.php`
`vendor/composer/installed.json` lists exactly `neuron-core/neuron-ai` and `psr/event-dispatcher`. If a dependency upgrade brings in a monitoring or HTTP package, this fails and says to check it for outbound data before updating the list (rule 8: an upgrade is its own deliberate PR).

### 6.3 New: `tests/Integration/ConcreteCmsLogObserverTest.php` (unit if `psr/log` loads without Concrete; otherwise integration)
With a recording PSR-3 logger passed in, the observer attached to a `ConcreteCmsAgent` with `observe()` for one fake turn (nothing written to `Logs`):
- logs each event's name with its `toArray()` data
- a `WorkflowError` carrying an `HttpException` whose request has `Authorization: Bearer <a configured test secret>`, and whose message quotes that secret: the logged context contains no object, no `request`, no `source` and no secret; the message is redacted
- no context value at any depth is an object
- red first: written against today's observer, the `HttpException` case fails

Secrets for the redaction case are passed to `SecretRedactor` as test values, not read from config (`SecretRedactorTest` does the same).
