Status: **approved. Glyn's answers are in section 8.**

## 1. How a package registers task permission keys in Concrete 9.5.5

All paths are under `httpdocs/concrete/`. Read, not run.

| Question | Answer | Where |
|---|---|---|
| What is a "task" permission? | A key with no permission object. One assignment (`PermissionAssignments`: key to access) holds the list of groups or users who have it. The core ones are the keys in the `admin`, `sitemap`, `marketplace` and `logs` categories. | `src/Permission/Key/AdminKey.php` (empty subclass of `Key`); `config/install/base/permissions.xml` (`<permissionkey ... category="admin">`, for example `access_task_permissions`, `access_api`, `view_in_maintenance_mode`) |
| Which category must our keys be in? | **`admin`.** The Tasks page lists and saves only four hard-coded categories (`sitemap`, `marketplace`, `admin`, `logs`). A key in a package-owned category would never appear there and would be dropped from the saved form. | `elements/permission/lists/miscellaneous.php` lines 5-8; `controllers/single_page/dashboard/system/permissions/tasks.php` `save()` |
| How is a key created? | `Key::add($category, $handle, $name, $description, $canTriggerWorkflow, $hasCustomClass, $pkg)`. It inserts into `PermissionKeys` with the package ID. No custom class is needed (`AdminKey` is used). | `src/Permission/Key/Key.php` `add()`, line 503 |
| How are default holders set? | Create an access (`Access::create($key)`), add a `GroupEntity::getOrCreate($group)` list item, then `$key->getPermissionAssignmentObject()->assignPermissionAccess($access)`. | Core precedent, `src/Updater/Migrations/Migrations/Version20150504000000.php` lines 34-47 (adds a key and gives it to Administrators); `src/Backup/ContentImporter/Importer/Routine/ImportPermissionsRoutine.php` (the XML route: `<permissionkey>` with `<access><group name=".."/></access>`, skipped when the handle already exists) |
| How does an existing install get new keys? | An upgrade runs the same code, guarded by `if (!Key::getByHandle(...))`. Core does this in migrations: `Version20230225150942.php` adds `access_api` only when missing. For a package, `Package::upgrade()` runs when the package version in the controller is higher than the installed one (`c5:package:update`). | the files named above; our `controller.php` `upgrade()` |
| What happens on uninstall? | The package item category for permission keys removes every key whose `pkgID` is the package's, in any category. | `src/Package/ItemCategory/PermissionKey.php`; `Key::getListByPackage()` (`pkgID = ?`, line 401); `Package::uninstall()` lines 649-662 |
| Where does it appear? | Dashboard, System & Settings, Permissions & Access, **Tasks** (`/dashboard/system/permissions/tasks`). Each key is a row: its name, and who holds it. Click it to open the access dialog and add groups or users. Viewing and saving need the `access_task_permissions` task. | `single_pages/dashboard/system/permissions/tasks.php`; `elements/permission/lists/miscellaneous.php` |
| How is a key checked for the current user? | `Key::getByHandle('handle')->validate()`. Core does exactly this (`src/Http/ResponseFactory.php` line 263, `view_in_maintenance_mode`). `validate()` returns true for the super user first, then false when no access is assigned, otherwise whether the user matches an entity in the access list. The answer is cached in the request cache (`permission/key/<handle>`), so tests flush `cache/request` after changing a user or an assignment. A missing key makes `getByHandle()` return null. | `src/Permission/Key/Key.php` `validate()`, line 550; `Assignment::getPermissionAccessObject()` |

Two consequences for us:
1. "Configure is super user only unless granted" needs no assignment at all: a key with no access list is true only for the super user (`validate()`).
2. A guest can be granted a key by an admin (Concrete offers the Guest group in the access dialog). `validate()` doesn't check that the user is registered, so `canUse()` keeps its own `isRegistered()` test (question 3).

## 3. The plan

### 3.1 Keys, installed by one idempotent routine
- New `src/Access/NeuronPermissions.php`: handle constants and `install(Package $pkg)`.
  - `use_neuron_ai`, name "Use Neuron AI assistant", description "Can open the Neuron AI chat panel and use the assistant."
  - `configure_neuron_ai`, name "Configure Neuron AI", description "Can change the Neuron AI API keys and settings."
  - Both in category `admin`, `pkgID` = this package, no custom class, no workflow.
- **Add only when missing, and assign defaults only when adding.** An existing key and its assignment are never touched, so an admin's choices survive every `upgrade()`.
- **Defaults:** `use_neuron_ai` gets the Administrators group (`ADMIN_GROUP_ID`). `configure_neuron_ai` gets no access list, so only the super user has it until an admin grants it.
- `Controller::install()` and `Controller::upgrade()` both call it. `pkgVersion` goes up (3.0.1 to 3.1.0) so that `c5:package:update` runs `upgrade()` on an existing install.
- Uninstall removes the keys by `pkgID` (section 1); nothing to write.

### 3.2 Access check
- `ChatAccess::canUse()`: registered, and the super user or `use_neuron_ai` validates. If the key doesn't exist (package files updated but `c5:package:update` not run), only the super user. `SETTINGS_PAGE_PATH` is removed.
- New `ChatAccess::canConfigure()` (or the same in `NeuronPermissions`): `configure_neuron_ai`, with the same registered and missing-key rules.
- **Unchanged:** the panel injection in `controller.php`, `refusalReason()`, the token logic, and every endpoint. They already call `canUse()`.

### 3.3 Settings page
- The settings page goes back to normal Concrete dashboard permissions: no override of its own.
- `view()` and `save()` both require `configure_neuron_ai`. Without it, `view()` shows only "You don't have permission to change Neuron AI settings." and no form, so the "Key set / Not set" statuses go only to people who may configure. `save()` keeps its CSRF check.
- A user also still needs to be able to open the dashboard page itself (Concrete's own view permission on `/dashboard`). The key doesn't replace that; the Tasks page and `SETUP.md` say so.
- `can_edit`, the disabled fieldset and the hidden-Save logic in the view are deleted.

### 3.4 Seed (`seed_test_content.php`)
- Creates a group **"Neuron Test Editors"** with a marker description, puts `neuron_chat_editor` in it, and adds that group to the `use_neuron_ai` access list. Nothing else: no page permission, no configure key.
- `neuron_editor` stays in no group. It is the no-access fixture.
- If the keys are missing (package not upgraded): a warning, and `neuron_chat_editor` has no panel access, as the seed already does when the page is missing.
- **`--reset` undoes it:** removes the group's list item from the `use_neuron_ai` access (leaving Administrators and anything an admin added), deletes the group (only one carrying the marker), and removes the orphan access entity the group left (the seed already has the same clean-up for users).
- **The settings-page override is removed.** The grant, `$inspectSettingsPage` as a gate, the foreign-override refusal and the reset bookkeeping all go. One piece stays for this release (dev only; it touches only rows this seed created; it can go in a later release, noted in PROGRESS): if the page still has the override this script made earlier (the exact signature the current code detects), both a normal run and `--reset` put it back to inheriting, so existing dev databases (this one, cID 439) are cleaned. A page that overrides in any other way is left alone with a warning, and the script no longer aborts because of it.
- The seed header comment and `SETUP.md` are updated.

## 4. Tests (PHPUnit, no provider calls, dev site, state restored)

New `TaskPermissionAccessTest`, using throwaway users and a throwaway group. It records each key's assignment first and restores it in `tearDown`, and flushes `cache/request` after each change:
- **Keys:** both exist, in category `admin`, `pkgID` = the package, handles and names as above.
- **Defaults on a clean install:** Administrators group has use; configure has no access list.
- **Use key, yes and no:** a registered user in a group granted `use_neuron_ai` passes `canUse()`; the same user outside it does not; removing the grant removes access. `neuron_editor` (no group) still does not.
- **Configure key, yes and no:** the same for `canConfigure()`, and `use` does not imply `configure` (a user with only use can chat but not save, and sees no form).
- **Guest refused:** with no grant, and with the key (temporarily) granted to the Guest group.
- **Super user always allowed:** with every assignment emptied, and with the keys missing.
- **Settings page:** the controller denies `view()` and `save()` without configure (nothing saved, no key status in the output) and accepts them with it; the existing CSRF and blank-save tests stay.
- **Existing install upgraded:** delete both keys (recording their state), call `NeuronPermissions::install()` (the same routine `upgrade()` calls), and check the keys exist with the defaults; call it again and check nothing changes; change the use assignment to a custom group, call it a third time, and check the custom assignment is untouched. Restored afterwards.
- **Seed:** run the seed and reset against the dev site; check the group, membership and `use` entry appear and disappear, and the settings page inherits again. Done as a recorded manual run (with a DB dump first), not as PHPUnit.

Rewritten: `ChatEditorAccessTest` (the chat user is in the seeded group, passes `canUse()`, can't configure, still has the same page rights as `neuron_editor`; the view-grant tests at lines 202, 267, 281, 297 and 319 replaced), `SettingsSavePermissionTest` (configure key instead of edit-page-properties; the page-permission restore code deleted).

**Real upgrade check (manual):** DB dump to `~/Herd/backups/` first; bump the version; `concrete/bin/concrete c5:package:update katalysis_neuron_ai` on the dev site (it has no keys today, so it exercises the upgrade path); confirm both rows in the Tasks dashboard page; run the seed; log in as `neuron_chat_editor` and `neuron_editor` in the browser (panel yes and no); log in as the super user and open settings. Full PHPUnit run, and scenarios 01, 02, 10, 12, 14, 15 once, to show nothing moved (they don't use `ChatAccess`, so this is a smoke check).

## 5. Behaviour change to record
Today anyone who can view the settings page can chat. On a default site that is Administrators only, which is what the default use key gives. A site that had given other groups view on that page will lose chat access for them after the upgrade until an admin grants the key on the Tasks page. This goes in the PR and in `SETUP.md`.

## 7. Recorded decisions

- **The launcher is paused.** It is not built. Revisit after P1.10a is merged: does the panel appear only where Concrete's toolbar shows (the toolbar button stays as it is), or everywhere, with a launcher of its own? The findings (the panel loads for anyone who passes `canUse()`; its only open and close button is injected into the Concrete toolbar, which many users never get) are in the P1.10a section of [DELIVERY_PLAN.md](../DELIVERY_PLAN.md) and in `/memories/repo/neuron_panel_visibility.md`. With task keys, a user with the use key and no toolbar will have a panel they can't collapse or reopen, so this is the first thing to decide after this merges.
- **The P1.11 decisions Glyn gave earlier stand** (the notice, the second text, the strong/weak scheme, no delimiters, scenario setup step B, the bar, separate commits; [P1.11.md](P1.11.md) section 2.0). **P1.11 follows P1.10a.** P1.11's only dependency on this task is the browser check as `neuron_chat_editor`, which this task makes work without a page grant.
- **P3.2 note: the tiers become additional task permission keys, not custom checks.** P3.2 adds keys for the higher tiers in the same `admin` category, installed by the same routine, with cumulative checks in code (a higher tier's key also passes a lower tier's check). `use_neuron_ai` is the Tier 1 (Content) key. Naming: P1.10a's `configure_neuron_ai` is the settings key; P3.2's "Configure" tier needs a different handle (the tier keys use `neuron_ai_tier_*` handles, decided by Glyn) so the two are not confused. P3.2's "Neuron AI – Content/Configure/Generate" groups then only exist as groups an admin may choose to grant these keys to; the code never checks a group.
