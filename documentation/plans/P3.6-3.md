Already on the branch, as Glyn asked: scenario 17's checks treat the approval cards as the confirmation. The new check `approvals_cover_children` is in its own commit, and 17's expected values are in another.

Glyn's decisions for the internal pilot:
- **Re-enabled behind approval:** `move_page`, `delete_page` (to the trash only), and `move_file_to_folder` (only as the delete redirect).
- **Still disabled:** `approve_page_version`, the three select-option tools, `delete_topic` and `delete_attribute_set`.

## 1. The re-enabled tools

Each tool runs its own checks in a dry run before the card is shown (`CallCheck`, P3.6-2). The dry run stops just before the tool triggers Concrete's request or moves the file, so a call that would be refused is never put to the user.

### `move_page`
- **Card:** "Move {page} ({path}) and its {n} pages below it under {target} ({path})". It then lists every page affected, with its title, old path and new path (B-CON-3). Old URLs keep working: the move saves the old paths, as Concrete's own move dialog offers (decision 1).
- **Fingerprint:**
  - the page: ID, parent ID, path;
  - its descendants: IDs and paths;
  - the target: ID, and the handles of its children;
  - the user's Move and Add Subpage permissions.
- **Refusals:**
  - as today: not found, a system page, edit mode, permissions;
  - new: the target is the page itself or one of its descendants;
  - new: a page with the same handle already exists under the target (as `create_page`).
- **Workflow:** goes through `MovePageRequest` (P3.6-2). The reply says "submitted for approval" when a workflow holds the move.

### `delete_page`
- **Card:** "Move {page} ({path}) and the {n} pages below it to the trash". It lists every page by title and path (B-T1-8, B-CON-3), and says how to restore them: Dashboard → Sitemap → Trash.
- **Fingerprint:**
  - the page: ID and path;
  - its descendants: IDs and paths;
  - whether the page is already in the trash;
  - the trash-can setting;
  - the user's Delete permission.
- **Refusals:**
  - as today: not found, a system page, edit mode, already in the trash, permission;
  - new: **the trash can is off** (`concrete.misc.enable_trash_can`). Concrete would then delete permanently, so nothing is deleted, and the refusal says so;
  - new (decision 2): the user's Delete permission on every descendant, not only on the page.
- **Workflow:** goes through `DeletePageCommand` and `DeletePageRequest` (P3.6-2).

### `move_file_to_folder` (only as the delete redirect, B-T1-11)
- **What changes:** the tool keeps its name (decision 3). Its only destination is "Assistant – to delete" under the file manager's root.
  - The tool finds that folder, or creates it if it's missing, subject to the user's Add File and folder permissions.
  - Any other `folderID` is refused: "This tool only moves files to 'Assistant – to delete' for a person to review and delete. Nothing was changed."
  - The description and the Files toolkit's guidelines say this. The guidelines are part of the prompt, so the prompt baseline changes (§3).
- **Card:** "Move {file name} from {folder} to 'Assistant – to delete', for a person to review and delete. Nothing is deleted. Anyone who can see that folder can see the file." When the folder doesn't exist yet, the card adds "(the folder is created first)".
- **Fingerprint:** the file's ID, its folder, the review folder's ID (or "missing"), and the permissions.
- **Refusals:**
  - as today: file not found, permission;
  - new: a destination other than the review folder;
  - new: the file is already in the review folder;
  - new: no permission to create the folder.

## Decisions (my recommendation in each)
1. **`move_page` keeps the old URLs as redirects** (Concrete's "save old page path"). The P1.13 reason was that a move broke links with no redirect.
2. **`delete_page` needs Delete on every descendant**, not only the page. That's stricter than Concrete's sitemap, which checks the page only. Recommended, because the card names every page.
3. **`move_file_to_folder` keeps its name**, but only the review folder is allowed. Renaming it (for example to `move_file_to_delete_folder`) would describe it better, but changes the tool baseline. Your call; I'd keep the name.
4. **Scenario 04's injected delete attempts:** with `delete_page` back, the runner's default `approval: approve` would approve an injected delete in 04. I propose letting a turn's `approval` be a map by tool, for example `{default: approve, delete_page: deny}`, and using that in 04. The runner change and 04's expected values would be in this PR.

## Risks
- **A delete held by a workflow:** if the trash can is turned off after the card but before a person approves the workflow, Concrete deletes permanently. Approval within the workflow is outside the assistant. The card and the reply say "submitted for approval".
- **Folder permissions:** moving a file into the review folder changes who can see it. The card says so.
- **Moving a large tree:** a long card. It lists every page, as B-CON-3 asks, and the block-limit warning style is reused: over the limit, the count comes first.
- **Baseline churn:** the prompt changes (the Files guidelines) and the tool list changes. Both go in their own commits.
