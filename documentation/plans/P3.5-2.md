# P3.5-2 Personal data: plan

**Goal:**
- **B-PII-2:** user and people reads return only the fields a request needs.
- **B-ACC-7:** `set_user_attribute_value` is removed, with a scenario showing user accounts stay read-only.
- **B-SEC-1:** no raw exception text from katalysis_pro reaches the model without SecretRedactor.

## 1. Fields: today and proposed
**The rule:** each read returns the identifying fields by default, and contact and private details only when the request asks for them, through a new optional input `fields` (a list).
- **Why an input and not a guess:** the model asks for a field when the person's request needs it ("email Robert" → `fields: ["email"]`). The tool description lists the extra fields.
- **What the default is for:** "who is…", "list the people/users" and "what does X do" are answered by the default fields.

| Tool | Today | Proposed default | Only with `fields` |
|---|---|---|---|
| `list_users`, `search_users` | id, username, **email**, isActive | id, username, isActive | email |
| `get_user` | id, username, **email**, isActive, dateAdded, **lastLogin**, **timezone**, **every user attribute** | id, username, isActive, dateAdded | email, lastLogin, timezone, `attributes` (named handles only; each needs Concrete's View User Attributes for that key) |
| `get_current_user` | as `get_user` (your own) | id, username, email, isActive (your own) | lastLogin, timezone, `attributes` (as above) |
| katalysis_pro `list_people` (replaces core's when installed) | sID, name, jobTitle, **email, phone, mobile, linkedin**, shortBiography, **biography**, qualification, active, featured, sortOrder, page, imageID, imagePath, imageUrl | sID, name, jobTitle, shortBiography, active, featured, page, imageUrl | email, phone, mobile, linkedin, biography, qualification, imageID, imagePath |
| katalysis_pro `get_person` | the same fields, one person | as `list_people`, plus qualification | as `list_people` |
| core `get_person_details` (live) and core `list_people` (used only without katalysis_pro) | email, phone, mobile, linkedin, image, relations | as `list_people`, with specialisms, topics and places | as `list_people` |
| katalysis_pro `list_places`, `get_place`, `list_reviews`, `get_review` | business and published data | **no change** (offices and published reviews; not personal data) | — |

- `search_users` still matches on email; it doesn't return the email unless asked.
- **Scenario 03** should move from partial to pass: its secondary check is that test emails aren't listed.
- **Scenario 21** asks "what do their bios say": the description of `list_people` says to add `biography`. If the model doesn't, more runs become `inconclusive` (P3.11-1). The risk is listed below.

**katalysis_pro's tools need a katalysis_pro PR** (`mapPerson()` and the `fields` input, against `themeintegrationtemplates`, as BF-12 did with #44); the core tools change here. The katalysis_pro PR merges first. Neither is usable alone without the scenario check.

## 3. katalysis_pro's `guarded()`: **on our side, no katalysis_pro PR needed**
katalysis_pro catches every exception and returns its raw message as `{ok: false, error}`, which skips `SecretRedactor` (P2.8). Every external tool already runs through our wrapper in `ExternalToolkitRegistry::build()`. That wrapper will pass the result through `SecretRedactor`: every string in an array result, and a thrown message too.
- **It covers any extension,** not just katalysis_pro. This is EXTENSIONS principle 3: the core applies the rule.
- **Test:** an external definition whose handler returns `{ok: false, error: "...<key>..."}`, and one that throws; neither shows the key.
- The P2.8 note is closed; nothing changes in katalysis_pro for it.

## Decisions (my recommendation)
1. **A `fields` input**, rather than a fixed smaller set: the request decides, and the default answers "who is…".
2. **Contact details are opt-in for people as well as users.** People profiles are often public on the site, but "list the people" doesn't need phones and emails.
3. **Places and reviews are unchanged:** they hold business data, not personal data.
4. **Each `get_user` attribute needs its own permission:** returned only when named, and only if the viewer has View User Attributes for that key, as Concrete's user search does.

## Tests
- **Red first:** for each changed read tool, one integration test that the default leaves out the opt-in fields and that `fields` returns them (`get_user` with an attribute the viewer may and may not see), and the redaction test.
- **Passing tests that change** (the tool baselines and the lists above): each in its own commit, with the reason. I'll ask before each one unless you approve them here.

## Risks
- Scenario 21 could become more often `inconclusive` if the model doesn't ask for biographies; P3.S1 will show it.

- `get_user` callers that relied on email being there: none in our code, but the model may need one more call.
