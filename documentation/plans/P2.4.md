# P2.4 plan: `instructions()` → `SystemMessage`, and the prompt on Neuron 4

Significant task (prompts). Base and PR target: `integration/neuron4` (Phase 2 Branching note). Branch `task/P2.4-system-message`, started 2026-10-21T22:26Z.

References: DELIVERY_PLAN P2.4 (with the guidelines-heading item from P2.3); [P2.1 findings](P2.1-findings.md) §4 (last row), §7, §9; [P2.2-upgrade-guides.md](P2.2-upgrade-guides.md) guides 24, 25, 26 and 57; PROGRESS P2.3 entry (known failures: `AgentPageContextTest` 4, assigned to P2.4).

## 1. Goal
The system prompt and the user message the model receives on Neuron 4 are **byte-for-byte what it received on Neuron 3**, proved by a test against a v3 capture, with `instructions()` returning a `SystemMessage` and the v3 cache workarounds gone.

## 2. Starting point (checked 2026-10-21, before any edit)
- `integration/neuron4` at `9eb361a` (P2.3 merged). `ConcreteCmsAgent::instructions()` returns a string; v4 wraps it in a `SystemMessage` (findings §9), so it already works.
- **v4 rebuilds the prompt for every turn:** `Agent::resources()` calls `resolveTools()` per execution segment, which clones `getInstructions()` (our `instructions()`, called afresh) and adds the toolkit guidelines as a second text block. Nothing is cached across turns, so `setRuntimePageContext()`'s three lines that reset v3's caches (`unset($this->instructions, $this->startEvent)`, `$this->toolsBootstrapCache = []`) do nothing useful; the last one creates a deprecated dynamic property, and `startEvent` is reserved on v4 (guide 57).
- **The page tag is unchanged on v4:** `handleUserMessage()` → `tagMessage()` → `handle()` → `new UserMessage(...)`. v4 adds nothing to a user message when `context()` is empty (ours is).
- **A whole turn runs on v4 without the database**, if the test gives the agent a thread ID and Neuron's `FakeAIProvider` (the default history is v4's in-memory store; our `setChatId()`/`chatHistory()` are not called). Checked with a read-only `c5:exec` probe (scratchpad, not committed): `handleUserMessage('Hello')` returned the fake reply, and the provider recorded the system prompt, the messages and 62 tools.

## 3. The prompt baseline (v3 against v4)
### 3.1 What was compared (probe, for this plan)
Fixed inputs: page `/neuron-test/headings` (as the panel would send it: ID and path), user `neuron_chat_editor` (set as the request's user with `Request::setCustomRequestUser()`: no login, no session, no write), message `Hello`. **Core toolkits only**: `ExternalToolkitRegistry`'s factories emptied (section 3.4 covers `katalysis_pro`).
- **v3:** `development` `b268f3b` (Neuron 3.15.26). `getStartEvent()->instructions` (the prompt with the guidelines, as v3's `ChatNode` hands it to the provider) and `UserMessage($agent->tagMessage('Hello'))`, both mapped by v3's OpenAI `MessageMapper` exactly as the provider does (`new Message(SYSTEM, $prompt)` first). The dev site was on `development` only for that run, then back on this branch, cache cleared.
- **v4:** this branch. A real turn through `handleUserMessage()` with `FakeAIProvider`; the system prompt and messages the provider was given, mapped by v4's `MessageMapper`.

### 3.2 Result
- **The user message (with the page tag) is identical:** `[Current page for this message: Headings, /neuron-test/headings, ID 12721. Earlier messages may refer to other pages.]\n\nHello`, as one text block.
- **The system message is one text block on both.** Identical: the whole of `instructions()` (identity, CURRENT CONTEXT with page and user lines, CAPABILITIES, GUIDELINES, TRUST BOUNDARY, RESPONSE STYLE), every toolkit's guideline text, every "Toolkit: X" line, the order of the toolkits and of the tools (62 on both). **Different (13,778 bytes on v3, 13,557 on v4):**

| # | Where | v3 | v4 | Cause |
|---|---|---|---|---|
| D1 | Between "- Concise and helpful" and `<TOOLS-GUIDELINES>` | one line break | a blank line (two line breaks) | v4 keeps the guidelines as a second text block of the `SystemMessage`, and `SystemMessage::getContent()` joins blocks with `\n\n`. v3 appended them to the string with one `PHP_EOL`. |
| D2 | The heading above each toolkit's guidelines (11 lines) | `# ` + the toolkit's class short name: `# FilteredToolkit` for the 9 toolkits that lost a tool to `DisabledTools` or a name clash, `# BlocksToolkit` and `# UsersToolkit` for the 2 that didn't | `# ` + the toolkit's offered tool names, comma-separated, e.g. `# list_users, get_user, get_current_user, search_users` | v4's `Agent::resolveTools()`; v3's `HandleTools::bootstrapTools()` (P2.1 findings §9). Why `FilteredToolkit` adds its "Toolkit: X" line: v3's heading hid the real name. |
| D3 | After each toolkit's guideline text (11 lists, 62 lines) | the toolkit's tool names, one per line; the first without `- `, the rest with it (v3 joins with `PHP_EOL.'- '`) | nothing (the names are in the heading instead, D2) | same |

Nothing else differs. The full v3 and v4 texts are in the scratchpad for this plan; the committed capture (5.2) reproduces them.

## 4. The guidelines heading (D1–D3): options
- **A. Keep v3's rendering exactly (recommended).** `ConcreteCmsAgent` overrides v4's `resolveTools()` (protected, not final: it returns the instructions and the tools) to build the guidelines block the way v3 did, as one text block: same heading (`# <class short name>`), same tool-name list, one line break before `<TOOLS-GUIDELINES>`. Tools are collected as v4 does (toolkits flattened, invisible tools dropped; none of ours is invisible). About 30 lines, all prompt rendering; `FilteredToolkit` keeps its "Toolkit: X" line (still needed, as the heading still says `FilteredToolkit`). **Result: no prompt difference at all.**
  - For: Phase 2 is a library upgrade; P2.9's scenarios then measure Neuron 4 alone, against the P1.5 baseline. P2.1 flagged the headings as a possible cause of wording shifts; with A that question can't arise. Prompt changes belong to P3.7, which is planned to rewrite the prompt with scenarios.
  - Against: we own the rendering (a v4 update that renames `resolveTools()` would silently fall back to v4's headings, but `PromptBaselineTest` would fail). It keeps v3's quirks (the `FilteredToolkit` heading, the first tool name without `- `) until P3.7.
- **B. Accept v4's rendering.** No override; D1–D3 stay, approved here, and the baseline test compares against v3 with exactly those three differences allowed. Drop `FilteredToolkit`'s "Toolkit: X" line, or keep it (then only 9 of 11 toolkits name their toolkit). Less code; the tool names move into the heading. P2.1's spike ran scenarios 10, 16 and 20 with v4's headings and no outcome moved, but that is 3 of 22 scenarios, and P2.9 would measure the heading change mixed with the library change.
- **C. A heading of our own** (e.g. `# PagesToolkit` with a clean `- name` list for every toolkit). A deliberate prompt change: belongs in P3.7, not here.

**Recommendation: A**, and note B/C for P3.7. If you choose B, sections 5 and 6 change as stated there.

## 5. Agent internals: what replaces what `AgentPageContextTest` used
| v3 (the test used) | v4 replacement |
|---|---|
| `getStartEvent()->instructions` (the prompt with guidelines) | what the provider is given on a real turn: `FakeAIProvider::getRecorded()[n]->systemPrompt`, with a thread ID and v4's in-memory history (no DB, no key, no network) |
| `resolveInstructions()` (prompt without guidelines) | `getInstructions()` (public, final on v4) |
| `bootstrapTools()` | the tools the provider was given: `getRecorded()[n]->tools` |
| `resolveState()->getChatHistory()` | `getChatHistory()` on the in-memory store, for now; **P2.5** points it at the `Chat` row store (`ChatMessageStore`) and adds the "stored row holds no instructions" check |

**`AgentPageContextTest` rewritten on v4**, same file and class, the same four behaviours, assertions kept where they still mean the same thing (each change listed in the PR):
1. A new page context replaces the old one on the next turn (two turns on one agent, headings then columns).
2. The guidelines block appears once and the tool list is the same after a context change.
3. The same context twice gives the same prompt; clearing it removes the page lines.
4. Restored history doesn't bring back an old page context: turn 1 on headings, then a **new agent** on the same thread and store, on columns. The prompt names columns only; the stored messages hold no instructions; the turn-1 user message keeps its headings tag (intended: "Earlier messages may refer to other pages"). The database part of this test moves to P2.5 (DELIVERY_PLAN line in the `PLAN:` commit).

**The page tag on every user message:** unchanged code path (2). The rewritten tests assert that each recorded request's newest user message starts with the tag for that turn's page, and that the turn-1 message in turn 2's request still carries its own tag. **v4's `context()` hook is not used:** moving the page context there is a prompt change (the tag would no longer be stored, and the CURRENT CONTEXT lines would leave the instructions). Proposed for P3.1 (ContextBuilder) or P3.7, with scenarios.

**Code changes in `src/ConcreteCmsAgent.php` (rule 3: planned here):**
- `instructions(): SystemMessage`, returning `new SystemMessage(<<<INST ... INST)`; the text is not changed by one character (guide 24).
- `setRuntimePageContext()`: remove the three v3 cache lines and rewrite its docblock (v4 builds the prompt for every turn). Guides 26 and 57.
- Option A: the `resolveTools()` override (section 4). Not with option B.
- Guide 25 (setters win over hooks): confirmed no change. We set `toolErrorHandler()` and `toolMaxRuns()` through setters and override no hook for them.
- Nothing else: history, `setChatId()`, `handle()`'s error path and `saveTurnNotice()` are P2.5 and P2.6.

The heading question moves to P3.7 (DELIVERY_PLAN line in the `PLAN:` commit).

3. **Q3: agreed.** The database half of `AgentPageContextTest` test 4 moves to P2.5.
4. **Q4: yes to `show_prompt.php`**, with three conditions: it refuses to run unless the site's canonical URL is a dev host (`ConcreteBoot::isDevHost()`, as the scenario runner does); it never prints the API key or another secret (everything it prints goes through `SecretRedactor`, and it never builds the real provider, so the key is never read); and it is covered by a test (`PromptPreviewTest`: the host refusal, the redaction, and a real run on the fixture page). Its logic is in `tests/Support/PromptPreview.php`, which `PromptBaselineTest` uses for its v4 turn too, so the script prints exactly what the baseline test checks.
5. **Q5:** `Who / tool / model` stays as its own field, alongside `Time` and `Scenario spend`.

## 12. Found during implementation
1. **`FilteredToolkit::guidelinesHeading()`** (a small method, not only the docblock as section 7 said). On v4 every core toolkit reaches the agent wrapped by `FilteredToolkit::built()` (P2.2: built once, for the scanner), so a plain class-name heading said `# FilteredToolkit` for `BlocksToolkit` and `UsersToolkit` too, where v3 said their own names. The method gives a `built()` stand-in its original's name and a filtered toolkit "FilteredToolkit", as v3 saw them. `PromptBaselineTest` caught it and covers it.
2. **`tests/Integration/ToolResultScanningTest.php`** (approved by Glyn during implementation): `testThePromptCarriesTheTrustBoundaryRuleOnce` called the protected `instructions()` by reflection and passed the result to `substr_count()`; with a `SystemMessage` it failed with a TypeError. It now reads `getInstructions()->getContent()`; both assertions unchanged.
3. The rewritten `AgentPageContextTest` was red before the code change on one assertion only: the instructions and what is sent agree, with one line break before `<TOOLS-GUIDELINES>` (v4's own rendering adds a blank line, D1). Its other three tests passed on v4 before the change, as expected (no prompt cache on v4).
