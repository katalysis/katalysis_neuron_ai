# P2.5 plan: chat history as a Neuron 4 message store

Significant task (DB schema, stored data, the agent's history). Base and PR target: `integration/neuron4` (Phase 2 Branching note). Branch `task/P2.5-message-store`, started 2026-10-21T22:47Z.

References: DELIVERY_PLAN P2.5 (repair, thread ID, the DB half of `AgentPageContextTest` test 4); [P2.1 findings](P2.1-findings.md) §3.3, §6, §7; PROGRESS P2.4 entry (known failures: `InjectionNoticeStorageTest` 8 and `PageContextTagTest` 2, assigned to P2.5); Neuron 4.1.12 source in `vendor/` (`Agent`, `ChatHistory`, `HistoryTrimmer`, `ChatNode`, `ToolNode`, `SQLMessageStore`, `Agent/AGENTS.md`).

**Decision taken into this plan (Glyn, in the task request):** there are no real users or installs. Existing dev chats need not survive the upgrade, and v3 rollback compatibility is not required. The dev chats are deleted and chat starts fresh. P2.9's rollback becomes "roll back the code and clear the dev chats".

## 1. Goal
Chat history on Neuron 4 is stored one row per message in a new table, through our own `MessageStoreInterface` implementation. Each row has a format version. `setChatId()` binds the agent's thread `chat-<id>`. A chat with two user messages in a row is repaired as it loads, before any provider call. The 10 known failures assigned to P2.5 pass.

## 2. Starting point (checked 2026-10-21, before any edit)
- **The agent can't use the database on v4.** `ConcreteCmsAgent::setChatId()` calls `chatHistory()`, which does `new DatabaseChatHistory()`. That class exists only on v3 (it is declared inside `if (class_exists(AbstractChatHistory::class))`), so on v4 the call fatals. That causes 8 of `InjectionNoticeStorageTest`'s failures and 2 of `PageContextTagTest`'s. v4 never calls `chatHistory()`: it reads `messageStore()` (default `InMemoryMessageStore`) and the thread from `setThreadId()`. `getChatHistory()` is `final` and builds a new `ChatHistory(store, thread)` on every call.
- **`resolveState()` does not exist on v4.** It is used by `saveTurnNotice()` (success path, inside a `catch (\Throwable)`, so on v4 the notice is silently never stored), by the agent's error path, by the controller's `send_message` (`saveAgentState()`, `history_count`, error recovery) and by the scenario runner. The error path, the controller's agent handling and the runner are P2.6. `saveTurnNotice()` is storage, so it is P2.5's.
- **How v4 writes history** (`ChatNode`, `ToolNode`, `InferenceNode`): the user message and the reply are committed only **after** the provider call succeeds, and a tool call and its result are committed together after the next provider call. A failed provider call stores nothing. Two user messages in a row can therefore no longer come from a failed turn on v4. They can still come from:
  - two requests on the same chat at once (two tabs). The lease is per process, and our workflow persistence is in memory, so each request reads `[…, A]` and commits its own `U, A` pair. Interleaved, that gives `U1, U2, A1, A2`.
  - our own code writing outside a turn, such as the fallback reply.

  `HistoryTrimmer::validateAlternation()` runs on `addMessage()`, i.e. **after** the provider call. A broken stored chat therefore costs a paid call on every attempt and then fails (findings §6.4).
- **Approvals (P3.6) write before suspending.** A thread waiting for approval legitimately ends with a `ToolCallMessage` holding pending calls. It is appended once, by message ID (idempotent), and the final outcome is read from the following `ToolResultMessage` (`AGENTS.md` §approvals). Neuron says cross-process approvals need "workflow persistence **and** a durable chat history".
- **Who reads the stored chat today:**
  - the panel's `load` and `current` endpoints, which send the stored JSON list to `chat-panel.js` (after `PageContextTag::stripFromHistoryJson()` and `InjectionNotice::annotateHistoryJson()`)
  - `chat_list`, which reads the summary columns and filters out rows whose `chatHistory` is empty
  - the `send_message` "clear" branch, which blanks the blob
  - `ScenarioRunner` (deletes its chats by `sessionId` prefix; reads history through `resolveState()`, which is P2.6's)
  - two old repair utilities in the package root, `validate_all_chats.php` and `repair_chat_history.php`, which edit v3 blobs

  There is **no dashboard page that lists chats** yet. P3.9 plans retention, an admin purge and the Doctrine-managed table.

## 3. Storage design: recommendation
**One row per message, in a new table `KatalysisNeuronAiChatMessages`, modelled on Neuron's own `SQLMessageStore` but keyed to the `Chat` row.** `KatalysisNeuronAiChats` stays as the chat header (owner, session, location, dates, first and last message, count). The `chatHistory` blob is no longer read or written.

| | Blob (keep `chatHistory`) | Row per message (recommended) |
|---|---|---|
| Simplicity of the store | Read, change and rewrite the whole JSON on every append, archive and flag. The spike's version is about 200 lines. | One `INSERT … ON DUPLICATE KEY` per append. One `UPDATE` per archive or flag. Ordering by ID. About the same size, and simpler to reason about. |
| Neuron's contract | Idempotent append by ID needs a scan. `loadAll($limit, $before)` decodes everything, then slices. | A unique index gives idempotency (as `SQLMessageStore` does). Pages are a `LIMIT` query. |
| Two writers at once | The last writer wins, so one request's messages are **lost** (the two-tab case above). | Both inserts land, and the repair (§6) makes the sequence valid. Nothing is lost. |
| Admin views (P3.9 retention and purge; a future transcript or usage view) | Purge by date works either way. Anything per message (search, tool calls per chat, token usage, which tool returned flagged text) means decoding every blob in PHP. | Plain SQL on `role`, `type`, `createdAt` and the JSON columns. Purge is `DELETE` on the header, and the rows cascade. |
| P3.6 approvals | The pending `ToolCallMessage` is somewhere in the blob. The approval fingerprint (DELIVERY_PLAN P3.6) has no natural home. | The pending call is a row with its own ID. The fingerprint can go in a column or a side table keyed by `(chatId, messageId)`. Rendering pending approvals after a refresh is a `loadAll(limit)` query. |
| Migration later | One blob per chat, rewritten whole | A `formatVersion` per row, so a migration touches exactly the rows that need it, in batches. |
| Cost now | Low | One new entity and table (package version bump), and the panel's `load`/`current` build the JSON list from rows. That list has the same shape as today, so `chat-panel.js`, `stripFromHistoryJson()` and `annotateHistoryJson()` keep their inputs. |

Not recommended: using `SQLMessageStore` itself. It needs a raw PDO, keys threads by a string with no link to the `Chat` row (so no cascade on delete), and has no format version. We copy its semantics (ordering, idempotency, archive marking), not the class.

### 3.1 The table (Doctrine entity `Katalysis\NeuronAi\Entity\ChatMessage`)
| Column | Type | Notes |
|---|---|---|
| `id` | BIGINT, auto-increment | Insertion order = thread order (as `SQLMessageStore`) |
| `chatId` | INT, FK → `KatalysisNeuronAiChats.id`, `ON DELETE CASCADE` | The thread `chat-<id>` |
| `messageId` | VARCHAR(64), `utf8mb4_bin` | Neuron's message ID (`msg_…`). Compared exactly, since `SQLMessageStore` warns that default collations ignore case. |
| `role` | VARCHAR(16) | `user` / `assistant` |
| `type` | VARCHAR(32), nullable | `tool_call`, `tool_call_result` or null (plain message), for SQL views |
| `content` | LONGTEXT, nullable | JSON: the content blocks |
| `meta` | LONGTEXT, nullable | JSON: the rest of `Message::jsonSerialize()` (`__meta`, `usage`, `tools`) |
| `formatVersion` | SMALLINT | §4 |
| `archivedAt` | DATETIME, nullable | Trimmed out of the model's context but kept (`loadAll`) |
| `createdAt` | DATETIME | |

Indexes: unique `(chatId, messageId)`; `(chatId, archivedAt)`.

The table is created by Doctrine through `c5:package:update` (package version 3.1.0 → 3.2.0). `controller.php`'s raw `CREATE TABLE` for the header table is left alone (P3.9).

### 3.2 The header table
`Chat` keeps its columns. `chatHistory` stays in the table and the entity, **unused**. Its getter and setter are marked deprecated, with a comment saying P3.9 drops the column with the Doctrine-managed table. Dropping it now would also mean changing the raw `CREATE TABLE` in `on_start()`, which is P3.9's.

The store keeps the summary columns as `DatabaseChatHistory` did: `firstMessage`, `lastMessage` (page tag stripped, 500 characters), `userMessageCount` and `updatedDate`. **One change (approved, §11.2):** `userMessageCount` counts the person's messages only. v3 also counted tool results, which have role `user`.

## 4. Format version
- Every row stores `formatVersion`. **1** = Neuron 4.1's `Message::jsonSerialize()`, split into `content` and `meta` as above. The constant is `ChatMessageStore::FORMAT_VERSION`.
- On read, a row with a **higher** version than the code knows is refused with a `ChatHistoryException` (a newer install's rows read by older code are never misread). A **lower** version goes through `ChatMessageStore::upgradeRow()`, which today has nothing to do and is the single place a future migration goes.
- Once real installs exist, a format change also adds a one-off batch migration in the package's `upgrade()`, by version, so rows aren't left to upgrade lazily for ever. That is recorded in the class docblock, and nothing is built for it now.

## 5. Thread binding: `setChatId()`
- `ConcreteCmsAgent::setChatId(?int $chatId)`:
  - with an ID: `setMessageStore(new ChatMessageStore(<the Connection>))` and `setThreadId(ChatMessageStore::threadFor($chatId))`, which is `chat-<id>`
  - with null: nothing changes (no thread, so v4's `chat()` throws "This agent has no thread ID", as Neuron intends)

  It returns `$this`, as now.
- `chatHistory()`, the `$chatHistoryInstance` property and the `DatabaseChatHistory` import are removed from the agent.
- **The thread ID is untrusted input** (`AGENTS.md`: the framework does no access control). `ChatMessageStore` accepts only `chat-` followed by digits, for an existing `Chat` row, and refuses anything else with a `ChatHistoryException`. Who may open which chat stays the controller's job, as today (`getOrCreateChatId()` by session; `load` by `createdBy`).
- `contextWindow()` is overridden to return **50,000**, as v3 used (v4's default is 100,000). v4's trim ratio (0.5) and archiving instead of deleting are kept (findings §6.5).

## 6. The repair
**What is repaired:** two plain user messages in a row in the **active** messages (a `UserMessage` that is not a `ToolResultMessage`). Between them the store puts a placeholder `AssistantMessage`, "[Recovered: the assistant's reply to this message was not saved]". It has no usage, and its ID is derived from the next message: `msg_recovered_<next messageId>`. Also two plain assistant replies in a row (the other half of the two-tab case, `U1, U2, A1, A2`), with a placeholder user message, "[Recovered: the message for this reply was not saved]" (Neuron rejects them, §11.1).

**Not repaired:** any other shape, in particular a thread ending in a `ToolCallMessage`. That is a legitimate pending approval in P3.6, and Neuron's own `abandon()` handles it. A shape the repair does not cover still fails as today, and is logged.

**Where:** in `ChatMessageStore::loadActive()`. That is the only way Neuron reads the conversation (`ChatHistory::getMessages()`), and `ChatNode` calls it to build the request **before** the provider call. So the repair happens before any provider call by construction, and the test in §8.2 proves it.

**Stored rows are not changed by the repair.** Loading never writes. The placeholder exists in memory only and is rebuilt the same way, with the same ID, on every load. Each repair is logged once per load (chat ID and position), through `SecretRedactor`.

**Keeping Neuron's archive count right:** `ChatHistory::addMessage()` archives "the oldest N active messages", counted on what `loadActive()` returned, placeholders included. So `archive($thread, N)` rebuilds the same repaired view, takes its first N entries and archives the stored rows among them (placeholders have no row). The store and Neuron's in-memory view therefore always agree, with no write on load.

`loadAll()` returns the stored messages as they are, without placeholders. The panel shows what was actually said.

## 8. Tests
### 8.1 New: `tests/Integration/ChatMessageStoreTest.php`
On throwaway `Chat` rows, deleted in `tearDown()` (the rows cascade; the leak check covers the new table automatically). The test maps the package's entities itself (findings §6.5).
- Append and load in order. Appending the same message ID twice stores it once. Two rows with the same `createdAt` come back in row ID order (§11.5).
- `loadActive()` leaves out archived rows, and `loadAll()` keeps them. `loadAll($limit, $before)` pages as `MessageStoreInterface` says, and an unknown `$before` gives nothing.
- `archive(N)` marks the oldest N active rows, and `clear()` removes the thread's rows.
- Round trip of each message kind, field by field: user (with the page tag), assistant (with usage), tool call (inputs, call ID), tool result (string result and `ToolOutput::error()`).
- The summary columns: first and last message with the tag stripped, and the count.
- **Format version:** rows are written with 1, and a row with version 99 is refused with a clear error.
- **Thread IDs refused:** `chat-abc`, `chat-`, `chat-1 `, `other-1`, a missing chat.
- Deleting the `Chat` row removes its messages (the cascade).
- `flagLastAssistantMessage()`: flags a plain final reply; refuses a tool call and a user message.

### 8.2 The repair (in `ChatMessageStoreTest`, plus one agent test)
- Stored `U, A, A` gives `U, A, P, A`, and stored `U1, U2, A1, A2` (the two-tab case) gives `U1, P, U2, A1, P, A2`.
- Stored `U, U, A`: `loadActive()` gives `U, P, U, A`. Neuron's `HistoryTrimmer` accepts the result (`trim(…, PHP_INT_MAX)` does not throw). **A checksum of the chat's rows (`CHECKSUM`-style hash of every column) is the same before and after the load:** loading never writes.
- Two loads give the same placeholder ID.
- `archive(2)` after a repaired load archives the first stored `U` only (the placeholder counts but has no row). The next `loadActive()` matches what Neuron kept.
- A thread ending in a pending `ToolCallMessage` is returned unchanged.
- **No provider call before the repair** (`AgentRepairBeforeProviderTest`, integration): a stored `U, U, A` chat, then a real turn through `handleUserMessage()` with Neuron's `FakeAIProvider`. The provider records each request. The first request already holds the repaired sequence (the placeholder is at position 1, and `HistoryTrimmer` accepts the request's messages as given), and there is exactly one request. The turn commits: the new `U, A` rows are stored, and the original rows are unchanged. **Red first:** with the repair switched off, the same turn throws "Invalid message sequence" **after** the provider has recorded a request, which is the v4 behaviour the plan fixes (findings §6.4).

## 10. Rollback (for P2.9)
If `integration/neuron4` is reverted after its merge into `development`:
1. Run `clear_dev_chats.php --apply` **before** reverting, after a backup. The script is removed by the revert.
2. Revert the merge.

v3 code then sees empty chats. The `KatalysisNeuronAiChatMessages` table stays behind. It is harmless (v3 never reads it, and deleting a chat still cascades), and it is reused if the upgrade is merged again. No data conversion is needed in either direction.
