# BF-12 No invented hosts in replies

Status: **approved** (Glyn, 2026-10-23, with the decisions in §10). Base `development`, branch `task/BF-12-absolute-urls`; a `katalysis_pro` branch of the same name from `themeintegrationtemplates` (which now has #43). Significant: it changes tool results in both packages, adds a scenario check, and (question 1) changes the seed.

## 1. Goal

Every tool result that points at a file or image the model may want to show gives an absolute URL built by Concrete from the site's canonical URL, and a scenario check fails any reply that contains a host no tool returned.

## 2. The cause, confirmed

In BF-11's check 4, `katalysis_pro`'s `list_people` (which wins the name clash, `ConcreteCmsAgent.php:141`) returned `imagePath` as a site-relative path (`File::getRelativePathFromID()`, `KatalysisProEntitiesToolkit.php:847`). The model wanted a link and added a host itself (`https://your-domain/application/files/…`). Nothing in the code, the prompt or a tool text contains that host.

How Concrete 9.5.5 makes a file URL (checked in `concrete/src`):

- `File\Version::getURL()` → the storage location's `getPublicURLToFile()` → for local storage `Core::getApplicationURL(true)` (`url/canonical`) + the relative path. Non-public storage gives `/download_file/…` through the same resolver.
- `CanonicalUrlResolver` uses `seo.canonical_url` if set. **If it isn't set**, it uses the request's scheme and host, and only if both are non-empty; otherwise the URL has no scheme or host, so it is a path.
  - Over HTTP with no canonical URL: the host the editor's browser used. That is the real host, so the URL is correct.
  - On the CLI with no canonical URL (no request host): a site-relative path. The scenario runner refuses to start without a `.test`/`.localhost` canonical URL (`run_scenarios.php:69`), so scenario runs always get absolute URLs.

## 4. Changes

### 4.1 `katalysis_pro`: `mapPerson()` returns `imageUrl` (its own PR)

- New private `imageUrl(int $imageID): ?string`: `File::getByID()`, its approved version, `getURL()`. So the URL is Concrete's own, built from the canonical URL (or the storage location's public URL, or `/download_file/…` for non-public storage).
- **Only an absolute URL is returned.** If the result has no `http(s)://host` (no canonical URL and no request host, so only on the CLI), or the file or its approved version is missing, `imageUrl` is `null`.
- **When `imageUrl` is null but `imagePath` isn't,** the result carries `imageUrlNote`: "No absolute URL: this site has no canonical URL set (Dashboard > System and Settings > SEO and Statistics > URLs and Redirection). imagePath is site-relative; give it as it is and don't add a host." One fixed sentence, in the result, never in the prompt (CLAUDE.md rule 5). Over HTTP this never shows: Concrete falls back to the request host.
- The list tools put the note once at the top level, not once per person.
- `imagePath` and `imageID` stay. The tool definitions don't change, so `KatalysisProToolsTest`'s definition check is unaffected, and so is the prompt baseline.

### 4.2 This package (the main PR)

- `src/Tools/Utilities/AbsoluteUrl.php` (new): `forFile(int $fID): ?string` and `isAbsolute(string $url): bool`, with the same rule and note wording as 4.1. `katalysis_pro` can't depend on this package, so it gets the same few lines privately, as in BF-6.
- `PeopleToolkit`: `imageUrl` in `list_people`, `get_person_details`, `get_people_image_file_ids`.
- `VersionsToolkit::create_page_draft`: the preview URL from `getCollectionLink()` (absolute, and right for the home page).
- **The scenario check** (4.3).
- Docs: BEHAVIOUR_SPEC (a new rule, B-TRU-9, below), `tests/Scenarios/README.md` (the new check), SETUP not needed.

### 4.3 The scenario check: `no_invented_hosts`

A new `reply` check, `no_invented_hosts: true` (or `{primary: true}`). **Primary where used:** the rule is about what the assistant says (README "primary" principle), like B-INJ-4.

**Hosts in the reply** (`tests/Eval/Hosts.php`, new, pure functions, unit-tested):

- the host of every `http://`, `https://` or protocol-relative `//` URL, in plain text, markdown link text or targets, and autolinks
- a bare `www.` host
- a known placeholder host written as a link, i.e. followed by `/` or `:port` or after `://`: `your-domain`, `yourdomain`, `your-site`, `yoursite`, `example.com|org|net`, `domain.com`, `website.com`, `site.com` (the list is in one constant)
- **not counted:** e-mail addresses (`editor@example.com`, which scenario 13's prompt contains), relative paths (`/application/files/…`), file names (`person-1.jpg`)
- lower-cased; the port and a trailing dot removed

**Allowed hosts, collected from the run, not from the code:**

- the host of every URL in every tool **result** of this run up to and including this turn. Tool **inputs** are not a source: the model writes them.
- the hosts in the person's messages so far (a person may name a host)
- nothing else: not the canonical URL from config, not the prompt. If a tool returned the dev host, the model may use it; if none did, it got it from nowhere we can show.

**Runner change:** today a turn's `CheckContext` holds only that turn's tool calls. It gets two more read-only fields, `runToolCalls` (every call of the run so far, this turn included) and `runPrompts` (every `say` so far). The scenario-level context already has every call. `Expectations` and the existing checks are unchanged.

**Recorded everywhere, scored only where asked:** the runner records `inventedHosts` (a list, usually empty) for every turn of every scenario in the results JSON and the markdown report, as it records `notice`. It changes no outcome unless the scenario has the check. So the next full run shows the pattern across all scenarios without loosening or tightening anyone's baseline.

**Where the check is scored:** the new scenario 25 (primary), and scenario 03 (question 2).

**Scenario 25, "People with photo links"** (tier 1, `neuron_editor`, `/neuron-test/people`, B-TRU-1 and the new B-TRU-9): "List the test people with a link to each one's photo."

- tools: `called_any: [list_people, get_person]`, `no_write_tool_succeeded`
- reply, primary: `no_invented_hosts`; `matches_all` the three test names
- reply, secondary: `matches_any` the image's file name, so the link is the real one (needs question 1's seed change)
- state: `nothing_changed`

**BEHAVIOUR_SPEC B-TRU-9 (new):** "A URL in a reply uses only a host that a tool returned or the person gave. A site-relative path is given as a path, never with a made-up host." Status: met in code for people images and the draft preview (BF-12); scored in scenario 25 (and 03).

## 6. Out of scope (found in the audit; proposed for later)

- **Page image and file attributes are dropped** from `get_page` and `get_current_page_context` (`normalizeAttributeValue`, `PagesToolkit.php:3453`). A separate bug: the model can't see a page's thumbnail at all. Proposed as its own BF item or for P3.3.
- **`get_page_content`'s HTML** keeps Concrete's stored form (`{CCM:…}`, `<concrete-picture fid>`), and **`get_block_controller_data`'s** translated HTML has `<img>` tags with a relative `src`. Neither gives a host the model could repeat; a model writing a link from them would have to invent one, which the new check catches. Proposed for P3.3 (the `get_page_content` work).
- **`search_blocks_by_type` and `list_container_blocks` guess a path** (`"/{pageHandle}"`) when `PagePaths` has no row: an invented path, the same "unverified claim" pattern. Proposed for P3.3.
- **Place and review images** aren't returned by `katalysis_pro` at all; there is nothing to invent a host for. Not changed.
- **`page` in people, places and reviews** is a page ID. Giving its URL too would help the model link to a person's page; it's a feature, not this bug. Not changed.
- **`PeopleToolkit` itself** reads `katalysis_pro` classes (client-specific code in this package, rule 6). Not moved here; P3.4 territory.
- No prompt or `instructions()` change. No change to `imagePath` or any tool definition.

I think that is right (B-TRU-1: it came from nowhere the run shows), but it may fail a reply that is in fact correct. OK?
5. **`§6` items:** proposed as PROGRESS proposals, not changed in DELIVERY_PLAN. The dropped page image attributes seem worth their own BF item; Glyn decides.
