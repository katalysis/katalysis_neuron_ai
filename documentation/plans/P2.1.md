### 3.2 How classes load today

The task brief says Concrete's autoloader wins. On this site that's only partly true.
- Concrete registers its loader first (`concrete/bootstrap/autoload.php`).
- Our `vendor/autoload.php` is required in `controller.php` `on_start` (lines 47–48). Its Composer loader **registers with prepend** (`vendor/composer/autoload_real.php:34`).
- So it's a race:
  - A class Concrete has already loaded by `on_start` (for example the PSR-7 interfaces used in request handling) comes from core.
  - Any class not loaded yet comes from **our** copy.

Packages in both vendors today, with different versions:

| Package | Ours (v3 bundle) | Concrete 9.5.5 core |
|---|---|---|
| `psr/http-message` | **2.0** | **1.1** (major mismatch; the 2.0 interfaces add return types) |
| `symfony/deprecation-contracts` | **v3.7.1** | **v2.5.4** (major) |
| guzzlehttp/guzzle, promises, psr7 | 7.15.1, 2.5.1, 2.13.0 | 7.15.5, 2.5.3, 2.13.1 |

That mismatch is a live risk with v3 today. It hasn't been seen to fail.

v4's only overlap with core is `psr/event-dispatcher`, at 1.0.0 in core. If that holds after install, **the upgrade removes the clash rather than adding one.**

The spike proves this at runtime. It doesn't infer it from `composer.json`:
- It diffs `installed.json` against core's.
- Under both web and CLI, it records which file each overlapping class and interface was actually loaded from (`ReflectionClass::getFileName()`), for:
  - `Psr\EventDispatcher\*`
  - anything in v4's `autoload.files`
  - any Guzzle or PSR-7 class still reachable from our code

  It records this both after a chat turn and after a settings save.

## 4. The tool contract

### 4.1 What breaks

Today every tool is built the same way:
- `new Tool(name, desc)`, or `new StrictInputTool(...)`
- then `->addProperty(new ToolProperty(...))`
- then `->setCallable($this->guarded(fn ...))`

There are no `Tool::make` calls. `katalysis_pro` builds its tools the same way.

In v4:
- `Tool` is abstract.
- `setCallable()` and the protected `$callback` are gone.
- `execute()` reflects on `__invoke()`'s parameter names and passes only declared properties.
- Validation errors become `ToolOutput::error(...)` and no longer reach `toolErrorHandler`.
- `approvalPolicy`, `invokeParameters` and `$result` are now reserved names on `Tool`.

### 4.2 Adapter shape

The spike builds two classes on `spike/P2.1-neuron4`:

- **`Katalysis\NeuronAi\Extension\ToolDefinition`**: our public, Neuron-free builder, as in EXTENSIONS.md.
  - `ToolDefinition::make(name, description)`
  - `->property(name, type, description, required)`, with our own type enum, not Neuron's `PropertyType`
  - `->handler(callable)`
  - `->writes()`
  - `->toNeuronTool()`, which the core calls, never extensions

- **`Katalysis\NeuronAi\Tools\Support\CallableTool extends NeuronAI\Tools\Tool`**: internal. It holds the closure.
  - **Option A (first try):** override `execute()`. Use the parent's input casting and required-property checks where they're reachable. Refuse undeclared inputs (StrictInputTool's rule, now for every tool). Call the closure with the declared inputs by name. Pass the result to `setResult()`.
  - **Option B, if `execute()` is final or the run loop bypasses it:** a generic `__invoke(...$args)`. Check whether v4's reflection passes named variadics.
  - **Option C, the fallback in DELIVERY_PLAN §4 step 4:** a generated subclass per tool. If C is the only option, it's a finding, and the spike stops building the adapter there.

To boot the whole agent without converting all 112 tools (that's P2.3), the spike branch also gets a temporary `LegacyTool extends CallableTool` that keeps the v3 surface (`addProperty`, `setCallable`). A scripted replacement of `new Tool(` with `new LegacyTool(` across `src/Tools/` then shows whether P2.3 can be one mechanical step. `get_page_content` and `update_page` are converted **by hand** to `ToolDefinition`, to prove the public contract.

### 4.3 How each Phase 1 layer survives

| Layer | v3 dependency today | v4 plan | Proven by |
|---|---|---|---|
| `guarded()` envelope | none (plain closure, a copy per toolkit) | unchanged inside the handler. Check what `setResult()` does with our array or JSON string: no double encoding | unit test on `CallableTool`; envelope seen in the stored tool result |
| `StrictInputTool` | overrides v3 `Tool::execute()` | the rule moves into `CallableTool`, so every tool refuses unknown inputs. Unknown keys no longer arrive at the closure but stay in `getInputs()`, so they can still be detected | unit test: unknown key refused, handler not called (scenario 09's failure mode) |
| `DisabledTools` / `FilteredToolkit` | `ToolkitInterface`, `AbstractToolkit::tools()` | both still exist in v4. Check `exclude()`/`only()` and the new duplicate-name exception | the existing `DisabledToolsTest` and `FilteredToolkitTest`, run unchanged |
| `ToolResultScanner` / `InjectionNotice` | **replaces the protected `Tool::$callback` with `Closure::bind`** (the most fragile layer; pinned by `ToolCallbackWrapSpikeTest`) | for our own tools, the scanner wraps the handler inside `CallableTool`, so there's no reflection on Neuron internals. For tools we don't build (external Neuron tools until P2.8), test the v4 hook: `AgentMiddleware::afterAgentNode` on `ToolNode`, which upstream marks as "inference, needs testing". `InjectionNotice` metadata must survive the v4 `__meta` move | `ToolResultScannerTest` adapted; the dev-site injection page shows the notice; scenario 16 |
| Draft isolation (`PageDraft::of`) | none (Concrete only) | unchanged | `DraftIsolationTest` unchanged; `update_page` leaves the live version unchanged |
| `ToolKind` | parses the envelope and our `toolErrorHandler` string | v4's `ToolOutput::error` text differs. `succeeded()` must classify both | `ToolClassificationTest`, plus one forced validation failure |
| `SecretRedactor` | none | unchanged. Check that `toolErrorHandler` still exists and still sees every exception, and where v4 validation errors go | `SecretRedactorTest`; a forced provider error with a fake key shows no key in the reply or the stored history |
| `PageContextTag` | none, but `stripFromHistoryJson` assumes the v3 stored shape | v4 reads v3 data, and new rows have `__meta`, block arrays and changed `tools` entries. Check `strip` on both shapes | `PageContextTagTest` with a v4-shaped fixture; scenario 20 |

Agent internals that change:
- `setRuntimePageContext()` unsets three v3 properties (`$instructions`, `$startEvent`, `$toolsBootstrapCache`).
- `instructions()` may now return `SystemMessage|string`, and string still works.
- `resolveState()` is gone, which affects the error path, `saveTurnNotice()` and the controller's `saveAgentState`.
- The `OpenAI` constructor's arguments have changed.
- A thread ID is now mandatory. We use the `Chat` `sessionId`.

## 5. Chat history

| | Ours (v3) | v4 |
|---|---|---|
| Contract | `DatabaseChatHistory extends AbstractChatHistory`, 6 hooks | `MessageStoreInterface`: `loadActive`, `loadAll`, `append` (skip a known message ID), `archive(count)`, `clear`. The `ChatHistory` class is concrete, and `getChatHistory()` is final |
| Storage | `KatalysisNeuronAiChats.chatHistory`: one JSON blob of v3 `Message::jsonSerialize()` per chat, plus counters and dates | built-in SQL store: one row per message, `message_id` unique per thread, `archived_at` |
| Trimming | deletes old messages | **archives** them, and by default cuts to half the window (`trimRatio 0.5`) |

**Proposal to test: keep our table, no migration.**
- A `ChatMessageStore implements MessageStoreInterface` backed by the `Chat` entity.
- It keeps the blob: `append` loads, adds and saves.
- Archived messages are kept in the same blob, marked in `__meta`, so `loadActive` filters them out.
- Upstream says v4 reads v3 message JSON unchanged.

The spike proves this two ways:
- It loads real v3 conversations already in the dev DB, not only new ones. **Read-only: stored rows are never rewritten** (12.1, condition 5). Each one is loaded into the v4 store and compared field by field. "Continues" (evidence 6) runs on an in-memory copy seeded from the row, so the row itself is not appended to. A checksum of each row's `chatHistory` and counters is taken before and after, and must match.
- It runs a new conversation across two separate processes (two HTTP requests, then a reload in the panel).

**Fallback, if the blob fights `append`/`archive` or the format won't round-trip:** a new message table and a one-off migration. That's a DB schema change and its own decision (Glyn).

The spike also records:
- which `trimRatio` matches today's behaviour
- whether `repairMessageSequence()` is still needed (v4's trimmer rejects a history that starts with a `ToolCallMessage`)

## 6. Approvals (for P3.6)

What v4 gives us:
- A per-tool `requireApproval()` or `approvalPolicy()`, which sees the bound inputs. A returned string is the reason.
- A run pauses with no exception: `AgentState::isInterrupted()`, with an `ApprovalRequest`.
- The decision is stored on each `ToolCallMessage` tool entry (`approval`, `approvalReason`, `rejectReason`).
- Resume is `pendingApprovals()` then `submitApprovalDecisions(...)->run()`.
- Starting a new turn while an approval is pending throws `RunInFlightException`.

What it seems to lack, which the spike checks and the findings list:
- **No preview of the change** (diff, draft link). P3.6 still needs `update_page` to produce a draft, or a dry-run result, before the decision. **The findings must answer** (12.1, condition 6) whether a preview can be built on v4's pause and resume (for example, the approval policy or an interrupt carrying a dry-run result or draft link that the panel shows before Approve/Deny), or whether it needs our own mechanism outside v4's approval flow, with the reasons from the source.
- **Cross-request resume needs durable workflow persistence.** The built-in backends are InMemory, File, Database (PDO table `workflow_store`), Eloquent and Redis. The Database one is a new table, which is a schema decision for P3.6.
- **Nothing ties approval to Concrete permissions or tiers.** That stays our check, inside the tool.
- **Batch semantics for multi-page changes** (scenario 17), and an audit record.
- **Streaming UI:** `stream()` ends with an `InterruptEvent`, and the chat panel would need Approve/Deny.

**Demonstration, only if the time box allows:** `update_page` with `requireApproval()`. One CLI process pauses. A second CLI process approves through the **File** store, with no schema change, and the draft appears. Otherwise this section of the findings is written from the source, and says so.
- The File store lives **outside the repo and outside the web root** (the Claude Code scratch directory, never under `httpdocs/`), and is **deleted when the demo is done** (12.1, condition 7). The findings record that it was deleted.

## 12. Risks and questions

### 12.1 Decisions (Glyn, 2026-10-21)

The questions as asked, each with the decision. Glyn approved the plan "as described", and added conditions 5–10.

1. **Which version to pin.** Asked: 4.1.13 was published 2026-10-20, and its only listed change is removing dev files from the release. I recommended the exact pin `4.1.13`, with the latest 4.1.x re-checked at P2.2; the alternative was 4.1.12.

2. **`katalysis_pro` under v4.** Asked: its toolkit calls `new Tool(...)->setCallable(...)`, which v4 doesn't have, so it will probably fail to load or fatal. This probably means P2.8, or a compatibility shim, must land with P2.2.
   - **Decision:** if its toolkit stops the site booting, the spike may add a **spike-only guard in our package** that skips an external toolkit that fails to register, and **logs it** (which package, which toolkit, the exception). It skips only the failing toolkit; loading isn't turned off wholesale. No edits to `katalysis_pro`.
   - **The P2.8/P2.2 sequencing goes in the findings as a proposed plan change.** `DELIVERY_PLAN.md` isn't edited.

   - **Decision:** approved as part of the plan. Pushed, never merged.

### 12.2 Risks

- **Young release.** 4.0.0 is three weeks old, and the 4.1.x line has had 13 patch releases. API details in the guides may already have moved. The spike works from the installed source, not from the guides.
- **The dev site runs the spike** while the spike branch is checked out. Alex's site is unaffected. The DB backup (step 0) and step 10 bring this one back.
- **Context window behaviour changes** (archive instead of delete, `trimRatio`). This can change what the model sees in long chats, and the scenarios are short. Flagged for P2.5.
- **OpenAI provider.** v4's `OpenAI` uses Chat Completions, as ours does. Its constructor and HTTP client are new (curl). The provider-error test (evidence 7) covers redaction on the new code path.
