# BF-11 plan: the panel shows replies as text, never as live HTML

Status: **approved** (Glyn, with the decisions in §11). Base `development`, branch `task/BF-11-reply-rendering`. Significant: the injection safety layer (Glyn). **Top priority; no non-dev install until it is merged** (DELIVERY_PLAN §6).

## 1. Goal
Nothing the model, a tool result, the server or the browser's saved history says can become markup, script, a form, a frame or an image in the panel. Replies keep the small formatting they use today (bold, italic, code, links, line breaks, "- " lists), built as DOM nodes from text. Only links to `http(s)`, `mailto` and relative URLs are allowed. A reload shows only the person's messages and the final replies, as the live reply does.

## 2. What the investigation found
- **Model output reaches the page as live HTML.** In headless Chrome, with the real `chat-panel.js` and a fake server: a reply's `<img src=x onerror=…>` ran; a quote in a markdown link's URL broke out of `href` and added an `onmouseover` that ran on hover; a `javascript:` link was made; a `<form>` with a password field and an `<iframe>` rendered; `"<h2>…</h2>"` showed as a heading (the browser check); `<script>` didn't run (`innerHTML` never runs it). Proof page: §7.
- **Why:** `addMessage()` puts `formatContent(content)` into `innerHTML`. `formatContent()` does no escaping: it only adds tags around the raw text. The same path renders the live reply, the server's history on every page load (stored, so it comes back after a reload), the browser's saved history, error messages, and the person's own messages.
- **Pre-existing:** v3's panel rendered replies the same way.
- **The in-between notes:** `historyForPanel()` returns every stored message (`ChatMessageStore::transcriptJson()`). The model's text on a tool-call message (chat 5461: "I will change it to "<h2>1 updated Seed Heading</h2>". Let me update that") shows as an assistant bubble. Tool results (role `user`) show nothing only because their text is empty. BF-7's reload after every change redraws the history straight after each edit turn, which is why the notes now show every time.

## 3. Content-Security-Policy (information only; no change in BF-11)
The dev site sends **no** `Content-Security-Policy` header: checked on `/neuron-test/headings` and the `/dashboard` redirect (`curl -D -`; only `X-Frame-Options: SAMEORIGIN`). Concrete 9.5.5's `concrete.security.misc.content_security_policy` is `false` by default, and `application/config` doesn't set it. A logged-in page wasn't checked, but it reads the same setting. So nothing in the browser would have blocked §2. A CSP for the panel would be defence in depth, a later task if wanted (it would have to allow Concrete's own inline scripts).

## 5. The formatter: `js/chat-format.js` (new)
A pure function from a string to data, with no DOM, so `node --test` can run it:

- `parse(text)` → a list of blocks: `{type: 'line', inline: [...]}` and `{type: 'list', items: [[...], ...]}` for consecutive "- " lines. Inline pieces are `{type: 'text', text}`, `{type: 'strong' | 'em' | 'code', text}`, `{type: 'link', text, href}` and `{type: 'br'}`. **Text is never HTML:** `<h2>` stays the five characters `<h2>`, shown as written.
- `safeHref(url)` → the URL or `null`. It uses the WHATWG `URL` parser, the one browsers use (`new URL(url, 'https://base.invalid/')`), so leading spaces and control characters, tabs or newlines inside the scheme, and mixed case are handled as the browser would handle them. Allowed: `http:`, `https:`, `mailto:`, and relative URLs (kept as written). Everything else (`javascript:`, `data:`, `vbscript:`, `file:`, …) gives `null`, and the link is shown as its plain text.
- **No images, ever:** there is no image piece. `![alt](url)` is shown as plain text, so nothing is fetched without a click.
- A browser-side `renderInto(container, blocks)` in the same file builds the nodes (`strong`, `em`, `code`, `a`, `br`, `ul`/`li`). It's the only code that makes elements from reply data, and it uses only `createElement`, `textContent`, `appendChild` and `setAttribute` (for `href`, `rel` and `target` on links whose `safeHref()` passed).
- **Loading:** the file sets `window.NeuronChatFormat` in the browser and `module.exports` under Node. `controller.php` adds a `<script>` for it before `chat-panel.js`, with BF-4's `?v=`.
- **Behaviour kept:** the same formatting as today, but now right where today's was wrong. Today a reply with one list item puts the whole reply inside `<ul>`. Bold and italic don't nest (as today); code is literal (no bold inside code).

**A choice for you:** you asked for "a pure string function" and for links "built as DOM elements". This plan does both by having the pure function return data, not an HTML string, and building the DOM from that. The alternative would be a pure function returning escaped HTML, still inserted with `innerHTML`. That would keep one HTML string path, which this plan removes.

## 6. Server: final replies only
- **`ChatMessageStore::conversationJson(threadId)` (new):** the same JSON as `transcriptJson()`, keeping only `UserMessage`s that aren't `ToolResultMessage`s, and `AssistantMessage`s that aren't `ToolCallMessage`s. Filtered by class, the same rule as the chat list's `role = 'user' AND type IS NULL`. `transcriptJson()` is unchanged, since tests and `show_prompt.php` use it.
- **`historyForPanel()`** ([controllers/chat.php](../../controllers/chat.php)) uses it. The injection notice is on the final reply (`flagLastAssistantMessage()`), so it still shows.
- **Scope:** this changes only what the panel is sent. What the model gets back from the store (tool calls and results included) is unchanged.

## 8. Tests, red first
- **`node --test tests/js/`.** Written against `parse()` and `safeHref()` before they exist, so they fail first. The red run is committed with the tests, and the stub exports appear in the code commit. Each payload case checks that **no** piece is a tag, that the text survives as text, and that any link's `href` passed `safeHref()`:
  - every payload in the proof table: `<img src=x onerror=…>`; `[t](javascript:…)`; the quote break-out `[t](https://a/" onmouseover="…)`; `<form><input type=password>`; `<iframe srcdoc=…>`; `"<h2>…</h2>"`; `<script>…</script>`
  - quote break-out with `'` as well as `"`, and with `>` (`[t](https://a/"><img src=x onerror=…>)`)
  - schemes: `javascript:`, `JaVaScRiPt:`, ` javascript:` (a leading space), `java\tscript:`, `java\nscript:`, `\x01javascript:`, `data:text/html,…`, `DATA:`, `vbscript:`, `file:///`; allowed: `https://…`, `HTTP://…`, `mailto:a@b.c`, `/dashboard`, `page`, `#x`, `?q=1`
  - `![x](https://elsewhere/?d=1)`: plain text, no link, no image
  - HTML entities (`&lt;img…&gt;`, `&#106;avascript:`) stay literal text
  - the formatting kept: bold, italic, code, a link, line breaks, a "- " list, and code containing `**`
- **`ChatControllerTest`** (red first):
  - a turn with a tool call that carries text, a tool result and a final reply: a reload returns only the person's message and the final reply, and `load` returns the same
  - an injection notice on the final reply still comes back after a reload (the existing notice test, which passes unchanged)
- **`ChatMessageStoreTest`:** `conversationJson()` keeps user messages and final replies in order and drops `ToolCallMessage` and `ToolResultMessage`; `transcriptJson()` is unchanged.
- **Existing tests:** none should change. If one does, I'll stop and ask first.
- **Tiers:** the fast tier and `node --test` after each change; the full suite and `node --test` before the PR.
- **Scenarios:** I propose none. The model, prompts and tools are unchanged; the scenarios call the agent, not the panel, and nothing they check changes. Your call, since this is a safety layer.
- **Manual:**
  - the proof page in headless Chrome: every check "not fired" or absent
  - browser checks on the dev site: a reply quoting `<h2>` shows the tags as text; a link from the assistant opens in a new tab; after an edit turn and its automatic reload, no in-between notes appear; the saved list and errors look as before

## 10. Risks and questions
1. **The returned-data design (§5):** your choice of the data structure (this plan) or an escaped HTML string.
2. **Scenarios:** none proposed (§8).
3. **`node --test` as a required check:** Alex needs Node 20+ on `PATH` (ServBay's Node 22 works here). If Node is missing, `/finish-task` reports "JS tests not run". Should it fail instead?

6. **A behaviour change:** a single "- " line no longer wraps the whole reply in a list (§5). Messages look slightly different, not worse.
