# P3.6-1 plan: the approval mechanism

Branch `task/P3.6-1-approval-mechanism`, base `development`. A plan stop: it adds the approval mechanism and two tables. Neuron 4.1.12 facts below are from `vendor/neuron-core/neuron-ai`, read for this plan.

## 1. Pause and resume, with our own layer
- **Which tools are gated.** `update_page`, `set_page_attribute_value` and `create_page` get `withApprovalPolicy()`, which returns a fixed reason string per tool. **It never returns `false` for a gated tool.**
  - Neuron re-runs the policy on every pass and on resume (`ToolNode.php:146,265-288`). A policy that returned `false` on resume would let the call run without approval.
  - A test checks the policy for every gated tool, in every state.
- **The pause.** `chat()` returns an `AgentState`. When `isInterrupted()` is true, `pendingApprovals()` gives each call's ID, tool name and inputs. Our `ApprovalService` then builds a preview and a fingerprint for each call (§4):
  - **The preview** comes from the tool's own `preview(inputs)`, which reads and never writes.
  - **The fingerprint** is a sha256 of the state the change depends on:

    | Tool | Fingerprint covers |
    |---|---|
    | `update_page` | page ID, newest version ID, current values of the fields the call names |
    | `set_page_attribute_value` | page ID, newest version ID, current value of the attribute |
    | `create_page` | parent ID, parent's newest version, child handles under the parent, and the user's permission to add a subpage there |
- **On Approve:**
  1. Recompute the fingerprint and compare it with the stored one. The row is marked decided atomically (`UPDATE … WHERE status = 'pending'`).
  2. **Equal:** `submitApprovalDecisions([callId => 'approve'])->run()`. The tool then runs as today, with all its checks (permissions, draft, text checks).
  3. **Different:** submit `['reject', 'The page changed after the preview, so nothing was changed. Show the user a new preview if they still want this.']`. The row becomes `stale`, and the panel says "Not done: the page changed since you saw the preview."
- **On Deny:** submit `['reject', <the user's optional reason, or "The user chose Deny.">]`. Neuron gives the model "TOOL NOT EXECUTED. The user rejected this action…" (`ToolNode.php:397-405`).
- **Several calls in one response:** Neuron holds the whole batch until every gated call is decided, and partial decisions re-suspend. The panel shows one card per call, and each is decided on its own.

## 2. Storage: two new tables (schema change)
Both are Doctrine entities, created by `c5:package:update`, like `ChatMessage`.

**Run state: `KatalysisNeuronAiWorkflowStore`**, Neuron's `DatabasePersistence` schema, unchanged:

| Column | Definition |
|---|---|
| `partition` | VARCHAR(510) ascii_bin |
| `key` | VARCHAR(510) ascii_bin |
| `value` | LONGTEXT ascii |
| `updated_at` | TIMESTAMP DEFAULT CURRENT_TIMESTAMP |
| Primary key | (`partition`, `key`) |

Neuron deletes a run's partition when the run completes.
- **Recommended over the File store:** `application/files` can be reached from the web.
- **Needs** the PDO in `ERRMODE_EXCEPTION` and a MySQL session in strict mode. I'll check both on the dev site first. If Concrete's connection doesn't qualify, we use a dedicated PDO with those settings.

**Approvals: `KatalysisNeuronAiApprovals`**, our audit and preview record:

| Column | Definition |
|---|---|
| `id` | bigint PK |
| `chatId` | FK to Chats, ON DELETE CASCADE |
| `callId` | varchar(64) utf8mb4_bin |
| `toolName` | varchar(64) |
| `inputs` | json text, redacted |
| `preview` | json text |
| `fingerprint` | char(64) |
| `status` | varchar(16): `pending`, `approved`, `denied`, `stale`, `not_approved` |
| `note` | text, nullable |
| `requestedBy` | int |
| `requestedAt` | datetime |
| `decidedBy` | int, nullable |
| `decidedAt` | datetime, nullable |
| Unique | (`chatId`, `callId`) |
| Index | (`chatId`, `status`) |

Retention follows the chat for now; P3.9-2 adds a purge.

## 3. A new message while a call waits (B-ERR-5, BF-9; Glyn's recommendation)
- **What happens:** `send_message` first rejects every pending call through `submitApprovalDecisions` with "The user sent a new message instead of approving; this was not done." and runs it. Their rows become `not_approved`, then the new message is handled as a normal turn.
- **What the panel shows:** for each card, "Not approved: you sent a new message, so this wasn't done."
- **Cost:** the rejection costs one extra inference. Its reply is stored but not shown. The alternative, discarding the run without inference, needs a hand-written tool result in history and Neuron's raw `abandon`; I don't recommend it.
- **Two tabs:** a second tab's stale approval is refused cleanly, because the row is no longer `pending`.
- **The generic error goes:** the `RunInFlightException` case never reaches the user as "I ran into an error".

## 4. The per-turn changes summary (Glyn, P3.S2)
- **`TurnChanges` is extended.** Each entry gains:
  - `versionID`, from the result's `versionState`;
  - `isNewPage`;
  - `kind` (`page`, `file`, `topic`, `version`), with an `object` label for the non-page kinds.

  It also gains a `refused[]` list (tool, target if known, a short redacted reason), covering failed writes and denied or stale approvals.
- **Coverage:** a recorder per offered write tool, enforced by a test listing every offered write tool (from `ToolKind`). **"Nothing was changed" is shown only if that test lists no unrecorded tool.** Until then, the line lists what was recorded and nothing else.
- **One shape for both uses.** A "change entry" (`{action, target title, path, details[], status}`) is used by:
  - **the preview card**, built before the write: "will";
  - **the "Changed: …" line**, built from `TurnChanges` after the turn: "did".

  The panel has one renderer for both, using `textContent` only (BF-11).
- **Kept with each message:** the line is stored in the assistant message's meta (`katalysis_changes`, JSON), as the injection notice is (`flagLastAssistantMessage`, its `$more` widened to JSON). `historyForPanel` restores it, so it survives the page reload.

## 5. What the user sees (buttons only; typed text never approves)
- **`update_page`:** "**Change page** Headings (/neuron-test/headings). Description: "old" → "new". Saved in a new unpublished version; nothing goes live until someone publishes it." **[Approve] [Deny]**
- **`set_page_attribute_value`:** "**Set** Meta Title **on** Headings (/neuron-test/headings): (empty) → "Headings Test Title". A new unpublished version." **[Approve] [Deny]**
- **`create_page`:** "**Create page** "Scenario Child" under Neuron Test (/neuron-test), page type Page, template Full. It will be unpublished: visitors won't see it until someone publishes it." **[Approve] [Deny]**

After a decision the buttons are replaced by "Approved", "Denied", "Not done: the page changed since the preview" or "Not approved: you sent a new message". Then the reply and its "Changed: …" line follow.

**Endpoint:** `POST /chat/decide {callId, decision: approve|deny, reason?}`, with `X-Neuron-Token`. It's checked against the chat's owner and the row's status. `chat/current` returns any pending cards, so a reload shows them.

## 6. Failed turn and the log listener
- **Failed turn:** `storeFailedTurn()` appends what `TurnChanges` recorded before the failure to `ERROR_REPLY`, redacted: "Before the error: changed Headings (/neuron-test/headings), unpublished version 3."
- **Log listener:** a PSR-14 listener on `ToolCalled` and on our approval events. It logs the tool, call ID, outcome and approval decision, passed through `SecretRedactor`, never inputs in full, to Concrete's log. This also covers P3.9's "PSR-14 logging listener".

## 7. Scenario runner and scenarios
- **The runner:** after each `say`, if the agent is paused, the runner applies the turn's `approval` (`approve` by default, per tests/Scenarios/README) through the same `ApprovalService` the panel uses. It repeats until the turn ends, at most 5 rounds.
- **New checks:**
  - `approval_asked: [tool]`
  - `approval_decided: approve|deny`
  - `no_write_without_approval`: every gated tool that ran had an approved row
- **Scenarios:** 08, 10, 14 and a new deny scenario (38: set a meta title, the user denies; nothing changes, and the reply says it wasn't done), ×3 each. That's 12 runs at $0.095, about $1.14, so I propose **a cap of $1.30** (the entry's $0.65 was priced at $0.07 for 9 runs).
- **Needs Glyn's agreement:** scenario 14's turn is changed to `approval: deny`, because the user asked only for a summary. That's an expected-value change, in its own commit. P3.6-2 adds its direct live-version check.

## 8. Risks
- **Two tabs on one chat:**
  - Both show the card, and the first decision wins; the second gets "already decided" (an atomic status update).
  - A message sent from tab B rejects the call tab A is showing; A's buttons then answer "no longer waiting".
- **The page changes before Approve:** someone edits the page, or another assistant call writes to it. The fingerprint differs, and the call is rejected as stale, with the reason given to the user and the model. There is still a small window between the check and the write. The tool's own checks (edit mode, permissions, text integrity) still apply inside it.
- **Policy drift:** covered by the fixed reason (§1) and its test.
- **Persistence:** the DB store's strict-mode and PDO requirements (§2) are checked first. A run left paused (the user walks away) holds its state until the next message rejects it.
- **The tools offered change between pause and approve** (the user's tier is revoked): Neuron's `resolveTool` fails. We catch it, mark the row `not_approved`, and tell the user.
- **Cost:** rejecting on a new message adds one inference per abandoned approval.
- **History:** the pending `ToolCallMessage` snapshot stays in history, as BF-9's repair expects. A test reloads a chat paused across processes.
