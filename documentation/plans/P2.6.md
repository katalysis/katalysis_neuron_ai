Significant task (the agent's error path, the chat endpoint, the injection notice and the runner; `BEHAVIOUR_SPEC.md` B-ERR-1, B-INJ-3, B-SEC-1). Base and PR target: `integration/neuron4` (Phase 2 Branching note). Branch `task/P2.6-agent-state-controller`, started 2026-10-21T23:13Z.

References: DELIVERY_PLAN P2.6 (the runner on the v4 API with a free `FakeAIProvider` dry run first; the thread bound before every `chat()`); PROGRESS P2.5 entry (chat in the panel stores the turn, then 500s at `saveAgentState()` → `resolveState()`; stale imports; `SeedResetTest` known failure); [P2.5 plan](P2.5.md) §2; [P2.1 findings](P2.1-findings.md) and the spike commit `2c79741` (the shape of the controller and runner changes); Neuron 4.1.12 source in `vendor/` (`Agent`, `ChatNode`, `ToolNode`, `ChatHistory`, `HistoryTrimmer`, `FakeAIProvider`).

## 1. Goal
Chat works end to end on Neuron 4: every chat endpoint answers with JSON that never carries a key, a stack trace or an internal path; a failed turn is stored as it was on v3; the injection notice and the page tag reach the panel and the store, proved by a test that goes through the controller; and the scenario runner runs on the v4 API, first free with a fake provider, then in a small paid smoke run.

## 2. Starting point (checked 2026-10-21, before any edit)
- **`resolveState()` is gone on v4** and is still called in four places: `controllers/chat.php` `saveAgentState()` (line 309), `history_count` (133), the controller's error recovery (145), `ConcreteCmsAgent::handle()`'s error path (625), and `ScenarioRunner::messages()` (274). Every successful panel turn is stored, then the request 500s at `saveAgentState()`.
- **Stale v3 code in the controller:** `use DatabaseChatHistory`, `use InMemoryChatHistory`, the `instanceof DatabaseChatHistory` warning, and the unsets of `$_SESSION['neuron_agent_state']` (nothing writes that key since v3's session state was dropped).
- **Thread binding is already one agent per request:** `getOrRestoreAgent()` builds a new `ConcreteCmsAgent` and calls `setChatId()` (P2.5), and the runner builds a new agent per turn and calls `setChatId()`. P2.6 keeps both and makes it explicit and tested.
- **How v4 stores a turn** (checked in `ChatNode` and `ToolNode`, "deferred pair-commit"):
  - the user message is committed only after the **first** provider call succeeds
  - a tool call and its result are committed together only after the **next** provider call succeeds
  - so a turn that fails on its first provider call stores **nothing**, and a turn that fails after a tool ran stores **only the user message** (the tool pair is dropped). History never ends on a dangling tool call (no approvals until P3.6).
- **On v3 a failed turn was stored as the user message plus "I ran into an error processing that request. Please try again."**, flagged with the injection notice when the turn had read flagged content. Today on v4 the error path throws inside its own `try` (no `resolveState()`), so it stores nothing and logs a warning.
- **Error replies that leak today:** `chat_list`, `load`, `current`, `new_chat`, `delete_chat` and `delete_current_chat` return `$e->getMessage()` to the browser on any exception. A Doctrine or PDO error message can hold SQL, table names and file paths. Their log lines aren't redacted either. (`send_message` already returns a fixed message and redacts its logs.)
- **Every action ends in `echo` + `exit`** (except the access refusal, which returns a response). That is why no test calls an allowed action today: `exit` would end PHPUnit. `ChatAccessTest` covers only the refusals.
- **`chat-panel.js`:** on a non-JSON reply it shows `Server returned <status> <text> with non-JSON content: <first 240 characters of the body>`. With Concrete's debug error page, that preview can hold an internal path or part of a stack trace.

## 3. The chat endpoint, action by action
Common to all actions:
- **Return a `JsonResponse` instead of `echo` + `exit`** (through one private helper, `json(array $body, int $status)`). Same JSON bodies, same status codes, same `Content-Type`. Needed so a test can call an allowed action in process (D1).
- **On an exception:** log `SecretRedactor::redact()` of the message (as `send_message` already does) and return a fixed message per action. Never `$e->getMessage()`, never a trace.
- The access check (`refuseIfNotAllowed`) stays first and unchanged.
- The request body is read from the controller's request (`$this->request->getContent()`) instead of `php://input`, so a test can supply it. Same bytes over HTTP.

## 4. The agent's error path (`ConcreteCmsAgent::handle()`)
Only the `catch` block changes (and `\Exception` → `\Throwable`). After a failed turn, through `getChatHistory()`, the v4 equivalent of `resolveState()->getChatHistory()`:
1. If the turn's own user message (the tagged one sent to the provider, matched by message ID) isn't stored, append it. (Failure on the first provider call.)
2. If the last message is then a user message, append the fixed reply "I ran into an error processing that request. Please try again." (Failure on any call.)
3. `saveTurnNotice()`, so a turn that read flagged content before failing carries the notice on the stored reply, as on v3.
4. Return the same fixed reply (the runner's `AGENT_ERROR_REPLY`, unchanged).

That keeps the v3 result: a failed turn is stored as the user's message plus the error reply, the person sees both after a reload, and the next turn starts from a valid sequence without needing P2.5's in-memory placeholder (D2). A failure inside this recovery is logged (redacted) and never thrown. The tool pair of a turn that failed after a tool ran is not stored (Neuron's pair-commit), so the model won't know about a draft that tool wrote. That draft is still undoable (Rule 7). Noted for P3.6, not fixed here.

## 5. The panel (`js/chat-panel.js`)
Nothing in the panel depends on v3. The fields it reads are unchanged: `success`, `response`, `notice`, `error`, `code` (send); `chat.chatHistory` with each message's `role`, `content` and `notice` (current, load); the list fields. `history_count` isn't read.

**One change proposed (D3):** in `sendMessage()`, a non-JSON reply shows only `Error: Could not connect to AI assistant. Server returned <status> <statusText>.`, without the 240-character body preview (lines 277–284). The preview is how a debug error page could show a path or a stack trace in the panel. If you'd rather keep the panel untouched in this PR, it can be its own small task.

## 6. The injection notice and the page tag through the controller
Both work at the agent level today (`InjectionNoticeStorageTest`, `PageContextTagTest`). BF-1 showed that this isn't enough: the controller's page context decides what the agent gets. The new `ChatControllerTest` (§8.1) calls `send_message` and `current` on the controller, with the `pageContext` body the panel sends, and an agent whose provider is `FakeAIProvider`. The provider asks for `get_page_content` on `/neuron-test/injection` (the real tool and the real scanner, on the seeded page), then replies. It checks:
- the reply JSON's `notice` is the fixed text naming "this page"
- the stored assistant row carries the notice kind and source
- `current` (the reload) returns the notice on that reply and on no other message
- the user message the provider received starts with the page tag for the page in `pageContext` (by ID, not the browser's title)
- the stored user row holds the tag, and `current` returns the message without it
- a second turn on a page with no injected text: `notice` is null and the first notice is still on the first reply

## 7. The scenario runner
- `ScenarioRunner::messages()`: `$agent->getChatHistory()->getMessages()`.
- **New messages by message ID, not by count.** v4 can archive messages when it trims, and P2.5's repair adds placeholders in memory, so "the messages after the old count" can drop or repeat messages. The runner notes the IDs before the turn and keeps the ones that are new.
- `toolCalls()`: the calls from each `ToolCallMessage::getToolCalls()`, each result from the following `ToolResultMessage`, matched by call ID (the spike's shape). A `ToolOutput` result is recorded as its JSON, which `ToolKind::succeeded()` already reads (P2.3).
- `usage()`: unchanged (`getUsage()` exists on v4; the store keeps usage, and `MessageDeserializer` restores it). The dry run checks that usage survives the store round trip.
- Thread: unchanged, a new agent and `setChatId()` before every turn, as the controller does. Commented as the v4 requirement.
- **Dry run (D4):** `run_scenarios.php -- --fake`. Each turn's agent gets a new `FakeAIProvider` that asks for `get_current_page_context` once and then replies "Dry run reply.", with made-up usage. It skips the API key check, records the model as "fake (dry run, no provider call)", and is free. The checks will mostly fail, because the replies are fake. What the dry run proves: every scenario runs to the end with no `error` outcome, tool calls and results are recorded, usage adds up, the chat rows are created and deleted, and the fixture resets between runs. Its result files are not committed.
- `SeedResetTest::testTwoScenarioRunsInARowNeedNoManualRepair` (the last P2.6 known failure) passes once `messages()` is on v4. No change to the test.

## 11. Risks and questions
- **D1. Return responses instead of `echo` + `exit` in every action.** This is needed for the controller test, and it touches every action, though mechanically. Concrete then sends the response and finishes the request normally (session write included), where `exit` cut it short. The browser checks (§12) cover the session. **Recommend: yes.**
- **D2. A failed turn is stored as the user message plus the error reply (v3 behaviour), not dropped (v4's default; the spike dropped it).** Storing keeps the person's message after a reload and the notice on a failed turn. **Recommend: store.**
- **D3. Drop the body preview from the panel's non-JSON error.** **Recommend: yes, in this PR.**
- **D4. Add `--fake` to the runner** for the free dry run. It also asks for approval, as every `run_scenarios` command does. **Recommend: yes.**
- **D5. Paid smoke run of 10, 16 and 22, once each, about $0.15**, after a clean dry run.
- `getOrRestoreAgent()` is renamed to say what it does. It's private, so nothing else calls it.
- Removing the controller's recovery block and `saveAgentState()` deletes about 45 lines of code that is broken on v4. Listed here for plan approval.
