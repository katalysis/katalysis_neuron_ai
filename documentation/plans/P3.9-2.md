# P3.9-2 plan: chat retention and admin purge (B-PII-5)

Branch `task/P3.9-2-chat-retention`, from `development`. It stops for a plan because it deletes personal data. #109 (ChatTableTest's import) is open beside it.

## 1. What is purged
A chat is purged as one unit, through one service, `ChatPurge`. A user's own delete uses it too, so every route removes the same things.

| Data | Where | How it goes |
|---|---|---|
| The chat | `KatalysisNeuronAiChats` | Deleted |
| Its messages, archived ones included | `KatalysisNeuronAiChatMessages` | `ON DELETE CASCADE` |
| The **Changed-line data** and injection notices | Each reply's `meta`, in those message rows | With the messages |
| Its approval records (inputs, previews, decisions) | `KatalysisNeuronAiApprovals` | `ON DELETE CASCADE` |
| Its paused run | `KatalysisNeuronAiWorkflowStore` (partition = the chat's thread) | `discardRun()` before the delete, as `delete_chat` does today |
| **Orphan runs** (a row whose chat is gone, or not updated within the retention period) | `KatalysisNeuronAiWorkflowStore` | A sweep in the same run, by `updated_at` |
| **Logs we write** (every tool call and decision, `ApprovalLogListener`, prefix "Katalysis Neuron AI: ") | Concrete's `Logs` table | Rows with that prefix older than the retention period. Other packages' and core's logs are not touched. |

**Not touched:**
- page versions, stack versions and files the assistant made: site content, under Concrete's own version history;
- the `katalysis.ai.*` settings.

**The browser's copy** (`localStorage`) clears itself: the panel already empties it when the server has no chat for the session.

## 2. The default and where it's set
- **90 days**, the setting `katalysis.ai.chat_retention_days`.
- It's on the Neuron AI settings page (Configure Neuron AI permission), in a new "Chat retention" section.
- It's checked on save, like the model (P3.8-1): a whole number from 1 to 3650. Keeping chats forever isn't offered, because B-PII-5 says older chats are deleted.
- **A chat's age is its last activity:** `updatedDate`, or `createdDate` if that's empty. A chat still in use isn't cut off 90 days after it started. **One schema addition:** an index `idx_updated_date` on the Chat entity, so the purge doesn't scan the whole table. It goes in with `c5:package:update`, version 3.6.0.

## 3. How the purge runs
- **A Concrete automated task**, "Purge old Neuron AI chats" (`neuron_ai_purge_chats`), installed with the package (install and upgrade). It runs on Concrete's task scheduler: Dashboard → System → Automation → Tasks, daily, with the site's `concrete:scheduler:run` cron. It can also be run by hand: `concrete/bin/concrete task:execute neuron_ai_purge_chats`. It purges by the retention setting and reports counts: chats, messages, approvals, runs, log lines.
- **Fallback (recommended):** many sites have no scheduler cron. So the chat endpoint also runs the same purge at most once a day, after a response has been sent: a timestamp in config plus a lock, a few DELETEs. Without it, the 90 days isn't enforced on those sites. *Alternative: task only, plus a warning on the settings page when the task has never run.*
- **Admin button, on the settings page** (Configure Neuron AI, the page's token):
  - "Purge chats older than N days now" (the setting).
  - "Delete all chats", for an incident.
  - **Confirmation is built into the page, with no browser `confirm()`:**
    - The first click only counts, and shows "This deletes N chats (M messages) from K users. This can't be undone." with a "Confirm delete" button.
    - That second post carries the counted cutoff and a one-time token. If more chats have aged into range since, it deletes only up to the counted cutoff.
    - The result says what was deleted, in counts.

## 4. What a user can delete themselves
- **Already there, kept:**
  - delete one of their own chats from the list;
  - "Delete current chat".
  - Both are limited to the owner (`createdBy`) and now go through `ChatPurge`, so the paused run and approvals go too. `delete_chat` already did that by cascade and `discardRun()`; the logs part is new.
- **New: "Delete all my chats"** in the panel's chat list, with the same in-panel two-step confirmation (count first, then confirm). It deletes only the user's own chats.
- **Logs on a user's delete:** a user's delete removes our log lines for their chat. The lines carry the chat ID, so they can be matched exactly. Admin purges match by age.

## 5. A chat with a call waiting for approval
- **When the purge reaches it** (older than the cutoff, or "Delete all"), its waiting calls are marked *not approved* and its run is ended (`discardRun()`, as for a deleted chat today). Then it's deleted. **Nothing that was waiting runs.**
- **Its owner then:** the card's buttons get the existing "This call is no longer waiting" answer (`decide` → recorded false), and a reload shows a fresh chat.
- **The scheduled purge skips any chat active in the last 10 minutes.** A chat that old by `updatedDate` can't be mid-turn, but this guards against clock edges. The admin's "Delete all" does not skip, and its confirmation counts the chats with a waiting call: "2 of them have a change waiting for approval; it won't be made."

## Tests (red first)
- **Purge:** old chats go with their messages, approvals, run and our old log lines; recent chats, other users' chats and other logs stay; the chat with a waiting call has its approval marked not approved and runs nothing.
- **Settings:** days outside 1–3650 are refused.
- **Admin purge:** needs Configure Neuron AI and the token; the first post deletes nothing and the confirm post deletes up to the counted cutoff.
- **"Delete all my chats":** only the owner's chats.
- **Task:** the controller runs the same purge.
- **Leak check:** each test makes and removes its own rows.

## Risks
- **Deleting is permanent.** Back up before trying it on a pilot site. The 90-day default applies from the first run after update, so **a site with chats older than 90 days loses them at the first purge**. PILOT.md will say so. *Alternative: a first-run grace period. I'd not add one.*
- **The fallback adds a small cost to one chat request a day.** It's bounded by a lock and a row limit per run (e.g. 500 chats; the next day continues).
- **Concrete's scheduler is off by default.** The task alone wouldn't enforce retention, which is why I recommend the fallback.
