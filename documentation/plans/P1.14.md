## 1. Goal

`seed_test_content.php --reset` and the scenario runner decide what is a fixture by something the assistant can't change, and
a reset discards any drafts on fixture pages, so no assistant edit can stop a reset or leave the dev site in a state it
won't clear. The dev-host guard and the final cache clear stay as they are.

## 2. Cause of the scenario 04 break

The seed's reset gets the page with `Page::getByPath('/neuron-test')` ([seed_test_content.php](../fixtures/seed_test_content.php) line 139)
and compares `getCollectionDescription()` with its marker text (line 356). `getByPath()` defaults to `'RECENT'`
(`concrete/src/Page/Page.php` line 319), which is the **newest version, draft or not**. Scenario 04's injected text made
`update_page` write a new description into a draft (version 2); the next reset read the draft, saw a different description,
and refused ("exists but was not created by this script. Nothing was deleted."). The refusal was correct for what it read;
what it read was wrong. `update_page` is the one tool that reaches it: its `description` and `name` write to the draft
([PagesToolkit.php](../../src/Tools/PagesToolkit.php) lines 2061 and 2068).

The dev database today is clean: all eight fixture pages have one approved version and no drafts.

## 4. Proposal

### 4.1 Identity is a stored ID

At the end of every successful run, and after each item is created, the seed stores one record of what it made:
root page `cID`; `uID` of both users; group `gID`; Express entity ID; file `fID`; the three `sID`s of the seed people.

- **Where:** the `Config` table, through the package's config repository, namespace `katalysis_neuron_ai`, one item `fixture.ids` (JSON).
  It is in the database, so a restored snapshot brings back the matching record. No tool in `src/Tools` writes `Config` (checked: the only `Config::` calls in `src/` are reads of the API-key
  and MCP settings). The spike confirms the exact call.
- **Not a file:** a file outside the database would drift from a restored snapshot.
- The description markers stay on the objects, written as now. They are for people reading the CMS and for the legacy path below. They no longer decide anything once an ID is stored.

### 4.2 Ownership rule, per item

1. **A stored ID, and that object exists:** it is ours, whatever its fields now say.
   - Root page: its path must still be `/neuron-test` and its parent the home page. If it was moved, or is in the trash, the reset refuses and says so (decisions 3 and 4 in section 10).
2. **No stored ID, or the stored object is gone:** look the object up by the old key. It is ours only if the old marker matches, **read from the approved version** for the page, never the newest. This is the one-time adoption path for sites seeded before P1.14 (this dev site, Alex's). Adopted objects get their IDs stored.
3. **Anything else at the old key** (something else at `/neuron-test`, a user `neuron_editor` that is not the stored one): not ours. The reset refuses and **deletes nothing**, as today.
4. Not found: nothing to delete.

### 4.3 Order in `--reset`

1. Dev-host guard (unchanged).
2. Find the owned objects by rule 4.2 (reads only).
3. **Discard drafts** on every owned page that has an approved version: each version that is unapproved and newer than the approved one, deleted with `Version::delete()` (the call `Page::delete()` makes for each version). Pages with no approved version (unpublished pages the assistant created) go with the tree. This runs only for pages owned by **stored ID**, before the legacy checks, so no drafts are discarded on a page the script then refuses to reset.
4. Legacy marker checks for what is not owned by ID (as today, now on the approved version). Any refusal aborts before anything is deleted.
5. The deletes and the permission clean-up, unchanged.
6. Clear the stored record, create everything again, store the new IDs.
7. Cache clear (unchanged).

`--reset-only` clears the record and stops. A plain run (no option) changes nothing on an existing site, except that it **adopts** by rule 2 and stores IDs if there are none; if adoption fails it warns and carries on, it does not fail.

### 4.4 What a reset does with an approved version edited by hand

With a stored ID the edit is no longer a reason to refuse: the ID is the proof of ownership and a reset's contract is "restore the known state". The reset **prints what it is throwing away**,
for example `/neuron-test: approved description differs from the seed text; discarded`, then restores everything. A hand edit made on purpose is lost, which is what a reset is for.
This applies to every item, so a user email, group description, Express name, file description or person name changed by hand no longer blocks it.

**Without a stored ID** (a legacy site) and with a hand-edited approved version, ownership can't be proved: the reset refuses, deletes nothing and says how to recover (put the description back, or delete the page by hand).

**Decided (section 10, decision 1):** proceed and report what is discarded.

## 8. Risks and questions

The two questions of the draft are answered in section 10.

Risks (as drafted; where a decision in section 10 changes one, section 10 wins):
- **New state in the database.** One `Config` row. It is removed by `--reset-only`; the leak check doesn't see it (the seed isn't a test). A DB snapshot restore brings the matching row.
- **A reset inside PHPUnit.** Fixture IDs change, so a test that kept an ID across classes would break. Existing classes look pages up by path, and `SeedResetTest` runs in its own process step. I will run the full suite to check. It adds several resets, which take a while; if too slow, it goes in its own group, run for this and the seed.
- **`Version::delete()` on drafts.** It is what `Page::delete()` calls, but a draft that shares blocks with the approved version needs checking: the spike (case 2) compares `Blocks` and `CollectionVersionBlocks` counts before and after.
- **Where the record lives.** The package config repository's exact namespace behaviour is confirmed by a spike before the rest is built. If it doesn't fit, a plain `Config` key under `katalysis.neuron_ai_fixture` is the fallback.
- **Trash.** On a site with the trash can on, a reset of a trashed root (ID matches, path in `/!trash`) must remove it from the trash too. Case 6's sibling in the spike; if it doesn't hold, it is reported.
- **First run on the dev site** adopts through rule 2, which needs the approved marker intact: it is (checked 21 October). A dump goes to `~/Herd/backups` before any run.

## 10. Decisions (Glyn, 21 October)

1. A hand-edited approved version with a stored ID: **proceed and report** what is discarded (4.4).
2. **Stored IDs for every seed item**, one mechanism.
3. The IDs are stored **in the database**, so a dump and restore stays consistent. The spike decides the exact place (Concrete's database config in the `Config` table, or a package-owned key) and records the choice in PROGRESS.md.
4. **Orphan blocks from `Version::delete()`:** rely on the P1.12 leak check. Report any table it flags. Do not allowlist it.
5. **A root page in the trash: refuse** with a clear message and delete nothing. This replaces the draft's "remove it from the trash too" risk.
6. **Tests leave the fixtures seeded when they finish.** Every `SeedResetTest` case ends with a clean `--reset` in `tearDownAfterClass()`, and a test that fails part-way still restores it.
7. Order of work: this plan as a `PLAN:` commit first; then test-first (cases 1, 3, 5 and 8 shown red before the fix); then scenario 04 with `--repeat=3`, confirming the reset between runs needs no manual repair; then the full PHPUnit run; then report before `/finish-task`.
