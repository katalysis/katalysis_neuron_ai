# P3.5-1 Per-object permission checks: plan

**Goal (B-ACC-4, B-ACC-5, B-ACC-6):** every write tool checks Concrete's own permission on the object it changes, before it acts. The 12 Blocks and Versions tools that never went through `guarded()` get a login check, the `{ok, data}` / `{ok: false, error}` envelope, and an object check. Three PRs: **A** the helper; **B** Pages, Blocks and Versions; **C** Files, Users, People, Topics and attributes. **Inventory:** today no `guarded()` checks more than login. `FilesToolkit`'s and `UsersToolkit`'s check nothing; Blocks and Versions have none. Their markdown error strings count as *success* to `ToolKind::succeeded()`, so `no_write_tool_succeeded` can't see a refusal.

## A. The helper: `src/Access/ObjectPermissions.php` (PR A, no tool changes)
One static function per check, named after the Concrete permission key. Each returns `null` when allowed, or a refusal message. `ObjectPermissions::deny(?string)` throws `PermissionRefused` (a `RuntimeException`) when given a message. Inside, each uses `new Checker($object)`, so it runs as the logged-in user. No super-user shortcut: Concrete's checker already allows super users.

| Function | Concrete key / check | Object |
|---|---|---|
| `viewPage`, `viewPageVersions`, `editPageContents`, `editPageProperties`, `editPageTemplate`, `approvePageVersions`, `deletePageVersions`, `deletePage`, `moveOrCopyPage` | `view_page`, `view_page_versions`, `edit_page_contents`, `edit_page_properties`, `edit_page_template`, `approve_page_versions`, `delete_page_versions`, `delete_page`, `move_or_copy_page` | Page |
| `addSubpage(Page $parent, ?Type $type)` | `add_subpage` (`canAddSubCollection($type)`) | parent Page |
| `addBlockToArea(Area, BlockType)` | `add_block_to_area` | Area |
| `viewBlock`, `editBlock`, `deleteBlock` | `view_block`, `edit_block`, `delete_block` | Block |
| `viewFileInFileManager`, `editFileProperties`, `deleteFile` | `view_file_in_file_manager`, `edit_file_properties`, `delete_file` | File |
| `addFile(folder)`, `editFileFolder(Node)` | `add_file` and `edit_file_folder` (Concrete's `canAddTreeSubNode` / `canEditTreeNode` on a folder; confirmed in PR A) | folder / file node |
| `addTopicTreeNode`, `editTopicTreeNode`, `deleteTopicTreeNode` | Concrete has no such keys: its topic node checks are access to Dashboard > Topics (`TopicTreeNodeResponse`; confirmed in PR A) | topic node |
| `addTopicTree()` | `add_topic_tree` task key (what Dashboard > Topics checks before adding a tree; replaces `viewDashboardPage` for `create_topic_tree`) | none |
| `viewDashboardPage(string $path)` | `view_page` on that Dashboard page: Concrete's own gate for attribute, set and topic-tree management | Dashboard page |

**Refusal message:** it says what was refused, the permission that is missing, who can grant it, and that nothing changed. It also tells the model not to try another route (B-ACC-6). For example: *"You don't have permission to edit page 123 (/neuron-test/locked): it needs Concrete's "Edit Page Contents" permission on that page. A site administrator can grant it in the page's Permissions. Nothing was changed. Tell the user; don't try another tool to make the same change."* The permission's display name comes from Concrete's key (`getPermissionKeyDisplayName()`), and the "where to grant it" text is fixed per object type. **Tests:** message text in a unit test; every function, allowed and denied, in an integration test using `neuron_editor` and a fixture page with a grant taken away (below).

## Decisions (with my recommendation)
1. **Attribute-key, set and topic-tree management** is gated by `view_page` on the matching Dashboard page, replacing super-user only. This is the gate Concrete itself uses, and admins grant it where they already manage it (B-ACC-3). It widens access only for users an admin has already let into those Dashboard pages.
2. **`update_page` and `set_page_attribute_value` check `edit_page_properties`**, which is the right key. The seed grants it to both test users, so scenario 10 is unaffected. A template change additionally needs `edit_page_template`, which the test users don't have: a deliberate refusal.
3. **Adding `editPageContents` to block writes** matches Concrete: a block can't be changed without edit mode.
4. **`discard_draft_version`:** your own draft needs `edit_page_contents`; someone else's needs `delete_page_versions`. Today any editor can discard anyone's draft.
5. **The envelope for the 12 tools:** ~~`{ok: true, data: {text: <today's markdown>}}`~~ changed by Glyn while building PR B: **success stays today's markdown text; every refusal or error becomes `{ok: false, error}`**. JSON-encoding the markdown would escape the block HTML these tools return (`<p class=\"x\">`, `\n`), the escaped text BF-7 found the model copying back into writes, and ToolResultEncoding would collapse the tables. ToolKind and the scenario checks still see every failure. Structured data waits for P3.3-4.
6. **No extra check on reads that already filter by view:** list, get and search tools that already check `canViewPage` / `canViewUser` keep that check. Only the gaps above are added.

## B-ACC-5 and B-ACC-6
- **B-ACC-5:** a test greps `src/` for elevation: `setCustomRequestUser`, `USER_SUPER_ID`, `loginByUserID`, `isSuperUser()` used as a bypass, `ignorePermissions`. Each hit is allowed only if listed with a reason. `FileAttributes`' bypass goes.
- **B-ACC-6:** tests that a refused write can't be reached another way: an editor refused `update_block_in_page_area` is refused by `batch_update_page_content` and by `move_block_between_areas`. A refused `delete_block…` can't be done with `batch_update_page_content` emptying the block. A refused `set_page_attribute_value` is refused through `update_page`'s `attributes`. A refused `delete_page` is refused by `move_page` to the trash.

## Risks
- Changed keys could refuse what an editor could do before: a template change; a discard of someone else's draft; attribute or topic work for non-super users who lack Dashboard access, which was already refused.
- The envelope changes the 12 tools' raw output, so scenarios 02 and 08 may word replies differently.
- The file-folder key names need confirming against Concrete 9.5.5 (PR A).
