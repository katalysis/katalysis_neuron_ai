# P3.9-1 plan: the chat table under Doctrine

Branch `task/P3.9-1-chat-table-doctrine`, stacked on P3.8-1 (#107; BF-21 #106 and P3.9-4 #105 below it), because each edits DELIVERY_PLAN. It stops for a plan because it changes the database schema.

## What's there today
- **`on_start()` runs `createDatabaseTables()` on every request:** a `CREATE TABLE IF NOT EXISTS KatalysisNeuronAiChats` that `install()` and `upgrade()` also run.
- **Doctrine already maps the table.** The `Chat` entity (`src/Entity/Chat.php`) is in the package's entity path, as `ChatMessage` and `Approval` are, so `c5:package:update` brings the table into line with the entity. The dev database shows this. Its table is the entity's, not the SQL's:
  - `sessionId` is nullable;
  - none of the SQL's three indexes is there (Doctrine dropped them);
  - `chatHistory` is still present.
- **The SQL and the entity disagree.** The SQL makes `sessionId` NOT NULL, but `makeSessionChat()` sets it to null. A fresh install gets whichever runs first.
- **`chatHistory`** has been unused since P2.5: messages are rows in `KatalysisNeuronAiChatMessages`. On the dev site it's empty in all 11 rows. On a site that ran v3 it can hold old chat blobs, which are personal data nothing reads.

## Changes
1. **`controller.php`:**
   - Remove `createDatabaseTables()` and its three calls, so the table is Doctrine's alone (install and upgrade run `installEntitiesDatabase()`).
   - Bump `pkgVersion` to **3.5.0** so upgrade runs.
2. **`src/Entity/Chat.php`:**
   - Remove `chatHistory` with its getter and setter (no caller left).
   - Add the indexes the SQL had, named as before, through `@ORM\Table(indexes=…)`:
     - `idx_session (sessionId)`: every request looks up the session's chat;
     - `idx_created_by (createdBy)`: the chat list;
     - `idx_created_date (createdDate)`: P3.9-2's retention purge.
3. **Dropping the column.** Concrete's schema update runs in safe mode and never drops a column. So `upgrade()` calls a small, idempotent `ChatTableMigration::dropLegacyChatHistory(Connection, table)`, which drops `chatHistory` only if it exists.
4. **Tests:**
   - **unit:** `controller.php` no longer contains `CREATE TABLE`;
   - **integration:**
     - the `Chat` metadata has no `chatHistory` and has the three indexes;
     - the migration drops the column on a scratch table (`neuron_test_p391_chats`, created and dropped by the test, so the leak check stays clean), and a second run is a no-op.
5. **SETUP:** after merge, back up, then `c5:package:update katalysis_neuron_ai` on each dev site.

## Decisions (with my recommendation)
- **Drop `chatHistory` in `upgrade()` (recommended), or leave the column unmapped?** Dropping removes unused personal data (helps P3.9-2 and B-PII-5) and the schema matches the entity. Leaving it is reversible, but keeps old blobs no tool can show or purge.
- **Keep the three indexes (recommended).** `sessionId` is read on every panel request, and P3.9-2 purges by `createdDate`.
- **Fresh installs:** Doctrine creates the table from the entity at install, as it already does for the messages and approvals tables. No SQL of our own.

## Risks
- **The drop can't be undone.** Back up first (SETUP, `backup_dev_db.sh`). Only the unused column is affected; the 11 dev rows keep every mapped value.
- **A site that skips `c5:package:update`** keeps `chatHistory` until it runs. Nothing reads it, so nothing breaks.
- **`on_start()` no longer heals a missing table.** The table only goes missing if someone deletes it, and install and upgrade create it.

## Scenarios
None, as the entry says. The full PHPUnit suite runs on the dev site after `c5:package:update`.
