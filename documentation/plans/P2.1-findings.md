Status: **draft for review (Glyn, Alex).** Plan: [P2.1.md](P2.1.md). Evidence, raw output and the scratch scripts: `documentation/plans/P2.1-evidence.md` on `spike/P2.1-neuron4` (pushed, never merged; last commit 9a64d4d). Spike: 2026-10-21, 10:53Z to 12:43Z.

## 1. Recommendation: go, with conditions

Move to Neuron 4. On the dev site, against the installed 4.1.12 source, every Phase 1 safety layer works on v4 without editing `vendor/`, the 60 core tools convert mechanically with identical names, descriptions and schemas, the stored v3 chats load and continue without a migration, and scenarios 10, 16 and 20 give the same outcomes and the same tool calls as at the Phase 1 exit.

Conditions (each is explained below):

1. **The vendor bump cannot merge on its own.** With v4 installed and nothing else changed, every page of the site returns 500 (5.1), and chat fails (5.2). P2.2, P2.3 (or the `LegacyTool` shim), P2.5 and P2.6 must reach `development` together, from the `upgrade/neuron-v4` branch the delivery plan already names (7).
2. **`katalysis_pro` must be converted (P2.8) before, or with, the upgrade**, or its 7 tools disappear (5.3). Proposed plan change in 7.
3. **A legacy broken-sequence repair, in memory, in the message store** (P2.5): v4 can't continue a stored chat that v3 left with two user messages in a row, and each attempt costs a provider call (6.4).
4. **`ext-curl` on production** (uk1 / Plesk): v4's only HTTP client by default. Not checked by the spike.
5. **Approval (P3.6) needs a mechanism of our own on top of v4's pause and resume** for draft-based previews and for tying the approval to what was previewed (8).

## 3. The tool contract

### 3.1 CallableTool and ToolDefinition (option A works)
- v4's `Tool` is abstract with **no constructor**; `execute()` is not final. `CallableTool` gives Neuron a variadic `__invoke()` and no signature (`invokeParameters()` returns `[]`), so v4's own `execute()` casts the inputs, settles a missing or mistyped input as `ToolOutput::error()` without running the tool, and passes every declared property by name, null when missing: the calling convention our v3 closures were written for. `guarded()` already returns a variadic closure, so v4's "declared default instead of null" rule can't reach our tools.
- The strict-input rule (StrictInputTool's) is in `CallableTool::execute()` for every tool; unknown keys stay in `getInputs()` on v4, so they can be detected. Thrown, so our error handler words it as in v3.
- `ToolDefinition` follows EXTENSIONS.md (`input()`, a handler taking one array); plan 4.2 said `property()`. `group()`, `tier()`, `permission()` and the handler's context argument are not in the spike (Phase 3 design). No Neuron type in its public methods (tested).
- Options B and C not needed.

### 3.2 Mechanical conversion (P2.3)
- A scripted `new Tool(` → `new LegacyTool(` (86 calls in 12 toolkits, plus the import) boots the agent. Offered tools: **v3 67, v4 62**. The 60 core tools are identical in name, description hash and schema hash; the difference is katalysis_pro's 7 (5.3). Plan evidence 5 said "112 minus the disabled ones": 112 is the defined total, 67 what is offered.
- So rule 4's registry test plus the scenarios can cover P2.3 as one mechanical step, as CLAUDE.md expects.
- Tests that build v3 tools (`new Tool(...)`) need the same swap: done on the spike for 35 calls in 7 test files, assertions unchanged (checked: the changed lines are identical once the swap is undone). It found one `LegacyTool` gap (v3's third constructor argument), fixed.
- v4 points to watch in P2.3:
  - duplicate tool names now **throw** (`ToolRegistry`); ToolNameResolver de-duplicates first, so fine today;
  - `exclude()`/`only()`/`with()` work by tool **class**; with one `CallableTool` class they can't tell tools apart. We filter by name already. **`with()` keeps one callback per class**: the scanner uses it, so anything else using `with()` on our tools replaces the scanner's hook (found in the approval demo). P2.3 should move the scanner off `with()` or forbid other uses;
  - v4 reserves `$parameters` (raw provider schema keys), `$inputs`, `$result`, `approvalPolicy()`, `invokeParameters()` on `Tool`.

### 3.3 Every file under `src/` must load
Doctrine's annotation driver `require_once`s every PHP file under the package's mapped `src/`. With v4 installed, `src/DatabaseChatHistory.php` (`extends AbstractChatHistory`, gone in v4) made **every page return 500, guests included**. Fixed on the spike by declaring the class only on v3 (katalysis_pro's own pattern). A load check of every Neuron-dependent file found no other. P2.2 must keep every `src/` file loadable, legacy `src/Toolkits/` included (it loads).

## 5. katalysis_pro under v4

### 5.1 It is not what broke the site
The 500 was ours (3.3). With that fixed, pages load; `katalysis_pro` loads, because its factory only does `new $toolkitClass()`.

### 5.2 It breaks every chat turn
Its toolkit builds v3 `Tool` objects in `provide()`, when the agent asks for tools, outside `ExternalToolkitRegistry`'s try: "Cannot instantiate abstract class NeuronAI\Tools\Tool" on every agent build.

### 5.3 The spike-only guard (12.1, decision 11)
`ExternalToolkitRegistry` calls each toolkit's `tools()` inside its try, and skips and logs one that fails. Logged on the dev site: `external toolkit ...KatalysisProEntitiesToolkit from provider "katalysis_pro_entities" skipped; its tools could not be built: Cannot instantiate abstract class NeuronAI\Tools\Tool`.
- Not offered as katalysis_pro's: `get_person`, `get_place`, `get_review`, `list_places`, `list_reviews` (missing) and `list_people`, `resolve_file_id_from_path` (the core versions come back; their descriptions and schemas differ).
- Failing because of it: `ToolRegistryTest::testDisabledToolsOfTheRealKatalysisProToolkitAreNotOffered`, `ToolRegistryTest::testEveryDisabledToolIsDefinedByAToolkitTheAgentLoads`, `ToolResultScanningTest::testListPeopleCarriesTheKeyForABiographyWithTheNote`, `ToolResultScanningTest::testListPeopleHasNoKeyForOrdinaryBiographies` (the core `list_people` has no `search` input: the strict-input rule working).

### 5.4 Should "skip and log a failing external toolkit" become permanent in P2.2?
**Yes, with two changes.** One package must not be able to break every chat turn, and the registry already catches a failing factory; this extends that to a toolkit that fails to build its tools. But:
- build each external toolkit's tools once per agent, inside the try, and hand the built list on, instead of calling `tools()` again later (today a second call would reconnect an MCP toolkit);
- make the skip visible beyond a log line: a warning on the settings page (and, later, the Extensions page in EXTENSIONS.md), so a silent loss of a package's tools is noticed. A test with a toolkit that throws.

### 6.3 Thread ID: `chat-<id>`, not `sessionId`
The plan said `sessionId`. It is the PHP `session_id()`: a live session token. On v4 the thread is the workflow identity and the storage key (a file name with the File store), and the CLI runner has no session. The spike uses the Chat row's ID.

### 6.4 Still needed: repair of legacy broken sequences (P2.5)
v3 rewrote a broken stored chat on load (`repairMessageSequence()` then save); v4 validates the sequence strictly. A throwaway chat holding user, user: v4 sent the request to the provider, then refused to commit ("Invalid message sequence at position 1: expected role assistant, got user"); every later turn on that chat fails the same way, after a provider call each time. New broken chats can't arise on v4 (a failed turn stores nothing), old ones can. Proposal: repair in memory in `loadActive()`, never writing.

### 6.5 Behaviour changes to note
- A failed turn is not stored at all on v4 (v3 stored the user's message, a fallback reply and the injection flag on it). The user still sees the fallback.
- Trimming archives instead of deleting, and cuts to half the window (`trimRatio` 0.5). Not exercised (short chats); the spike keeps the 50,000-token window. For P2.5.
- Test order: the storage tests depend on another class mapping the package's entities first (PHPUnit doesn't start packages). Not a v4 issue; each storage test class should map them itself, as `ChatMessageStoreTest` does.

## 8. Approvals, for P3.6

### 8.1 Demonstrated across two processes (File store)
`update_page` with an approval policy, FakeAIProvider as the model, history through ChatMessageStore, run state in v4's File store in the scratch folder (outside the repo and the web root):
- process 1: the turn paused before any write; the approval request carried the reason (a preview, 8.2); the stored tool call was marked pending; one store file, named after the thread;
- process 2 (cold): `pendingApprovals()` rebuilt the request from the store; a new turn while pending was refused (`RunInFlightException`); approving ran the tool: a new unapproved version, the live one unchanged; history: pending snapshot, then the approved result;
- cleanup: page, chat row and **store directory deleted** (checked).
Not tried: rejection with feedback, a multi-call batch (scenario 17), streaming, the Database store (`workflow_store` table, a P3.6 schema decision).

### 8.2 Can the change preview be built on v4's pause and resume?
**Partly. A text preview can; a draft-based preview, and an approval tied to what was previewed, need our own mechanism.**
- What v4 gives: the approval policy runs on a copy of the tool with the typed inputs bound, before execution, and a string it returns becomes the approval reason: shown on the `ApprovalRequest` action, persisted in the history (`approvalReason`), rebuilt by `pendingApprovals()` in a cold process. The demo's preview ("description "Old description" -> "New description"") went through all of that.
- Its limits:
  - it is one string: no field for a structured diff or a draft link (a JSON string would work, but it is free text to v4);
  - the policy must not write anything: v4 asks it on every pass, and again on resume (it ran once in each process), so it can compute a dry run but can't create the draft a preview would link to;
  - approval is bound to the call ID, not to the preview: on resume the policy is re-evaluated against the live page, so if the page changed in between, the tool runs against the new state the approver never saw.
- So for P3.6: use v4's pause and resume (it is durable and frontend-ready), with our own layer for (a) a preview the tool computes without writing, stored with a hash of the state it was computed from, and (b) a check on resume that the hash still matches, refusing otherwise. Writes that already go to a draft (P1.8) may not need approval at all; approval then gates the live-changing tools (publish, delete, move), which is where Phase 1 disabled them.
- Also still ours: Concrete permissions and tiers (inside the tool), batch semantics, an audit record, and the panel's Approve/Deny (v4's stream ends with an `InterruptEvent`).
