# P3.2-1 Tier keys and tier gating: plan

**Goal:**
- **B-ACC-9:** two new task permission keys, so there are three tiers. Tiers are cumulative and superusers get Tier 3.
- **B-ACC-2:** a tool is offered only if the user's tier allows it.
- **B-T2-6:** attribute definitions, attribute sets and topic trees leave Tier 1.
- **B-ACC-8:** external tools declare a tier. A write tool that declares none is admin-only.

**Panel (Glyn, 28 October 2026):** the panel stays where Concrete shows the toolbar (P1.10a), not everywhere. `ChatAccess::canShowPanelOn()` is unchanged apart from the tier check. Recorded in BEHAVIOUR_SPEC B-ACC-1, in this commit.

## 1. Keys, install and upgrade
- **The two new keys** (`NeuronPermissions`):
  - `neuron_ai_tier_configure` ("Neuron AI tier 2: Configure")
  - `neuron_ai_tier_generate` ("Neuron AI tier 3: Generate")

  They work like P1.10a's keys: in the `admin` category, carrying the package ID, and listed under Tasks.
- **Install and upgrade:** `NeuronPermissions::install()` adds any key that is missing and sets its default holders only when it adds the key. An admin's later choices are never changed. The package version goes from 3.2.0 to 3.3.0, so each dev site runs `c5:package:update`.
- **Default holders.** Recommendation:
  - **Configure:** the Administrators group. Admins have the Tier 2 tools today through `use_neuron_ai`, so this keeps what they have.
  - **Generate:** nobody but the super user (no access list). No Tier 3 tools exist yet.
- **The cumulative check:** `NeuronPermissions::tier(): int` works down this list and returns the first that applies:
  1. a guest gets 0
  2. the super user gets 3
  3. a holder of `neuron_ai_tier_generate` gets 3
  4. a holder of `neuron_ai_tier_configure` gets 2
  5. a holder of `use_neuron_ai` gets 1
  6. anyone else gets 0

  A key that isn't installed counts as not held.
- **`ChatAccess::canUse()` becomes `tier() >= 1`.** So a user who holds only the Configure key can use the assistant too, as "cumulative" requires. The task permission check also applies to the endpoints, as it does today.

**Gating** (`src/Access/TierGate.php`, in `ConcreteCmsAgent::tools()` after `DisabledTools`):
- It removes every tool above the user's tier, using the same `FilteredToolkit` mechanism, so a tool that is removed isn't in the prompt either.
- A toolkit with no tools left is dropped, guidelines and all.
- The runner runs the agent in-process as the scenario's user, so the gate applies to it too.

## 3. External tools (B-ACC-8)
- **Declaring a tier:** `ToolDefinition::tier(Tier $tier)`, with a new enum `Katalysis\NeuronAi\Extension\Tier` (`CONTENT`, `CONFIGURE`, `GENERATE`), as EXTENSIONS.md shows. `ExternalToolkitBuild` records each external tool's effective tier. On a name clash the external tool wins (as it does today), with its own tier.
- **A tool that declares no tier:**
  - a write gets Tier 3 (admin-only)
  - a read gets Tier 1

  "Write" means `writes()` was set or the name reads as a write (`ToolKind::isWrite`). Tools from the older `registerToolkitFactory()` path (Neuron toolkits, used today only by `McpServerIntegration`, which P3.3-3 deletes) get the same rule.
  - **Recommendation:** admin-only means the Tier 3 key (the super user plus anyone an admin grants it to).
  - **Alternative:** the super user only.
- **katalysis_pro:** declares no tiers today. Its reads stay Tier 1 and its writes (`add_person`, `update_person`, `delete_person`, `delete_all_people`, all disabled) become Tier 3.
  - **Recommendation:** no katalysis_pro PR here. Its `->tier()` calls go with P5.0's contract work, so the P5.0 entry gets one line (proposed in the PR).
