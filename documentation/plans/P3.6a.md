# P3.6a plan: stack and global-area editing

Branch `task/P3.6a-stack-editing`, stacked on BF-22 (PR #94, which edits DELIVERY_PLAN). It retargets to `development` when #94 merges. This task stops for a plan because it changes the permission and approval mechanisms (B-WRT-5). There are no schema or dependency changes.

## 1. What changes, by entry item
- **Switch on, block tools only.** `SystemPageGuard::stackEditingEnabled()` returns true.
  - `refuse()` gains `allowStack` (default false). Only the five block tools pass true: add, update, delete, move and the batch tool.
  - Every other tool still refuses a stack: update_page, the attribute tools, move_page, delete_page and the version tools.
  - System single pages and page type defaults stay refused permanently.
- **Draft only.** A new helper, `Utilities/SharedArea.php`, resolves a page and area handle, or a stack page directly, to the stack, as Concrete's edit-mode controllers do:
  - It takes the stack's `getVersionToModify()`.
  - Through a page, it calls `relateVersionEdits` to the page's draft, so publishing the page publishes the stack version. Concrete approves it only for someone with "Approve page versions" on the stack.
  - Directly on a stack page, the version is approved under Stacks & Global Areas. The assistant never approves either; `approve_page_version` stays disabled.
  - Add, update, delete and move write into that stack version. Delete gets its own path here, because the core command looks in the page's draft (BF-2 2.2).
  - The dry run stops before the stack version is made (`PageDraft::stopIfDryRun()`).
  - `DraftCleanup` also removes an empty stack version that a failed call made.
- **The user's permissions** on the stack, checked after the page's own checks:
  - `canEditPageContents` on the stack page;
  - for add, `canAddBlockToArea` on the stack's Main area;
  - for edit and delete, `canEditBlock` and `canDeleteBlock` on the stack's block;
  - `EditModeGuard` on the stack (checked out under Stacks & Global Areas).

  The refusal names the stack and the missing permission (P3.5-1 wording).
- **Concrete's permissions alone (Glyn's question).** First commit, red: with the switch on and no stack checks, `neuron_editor` adds a block through a global area. The test records whether Concrete stops it. The PR reports the answer, and the explicit checks go in whatever it says.
- **Another user's pending stack version.** `DraftOwner::of()` runs on the stack's newest version, so the card warns: "{stack} already has unpublished changes by {user} (version N, date). Your change is added to that version." It also lists what that version changes.
  - **Recommend warn, not refuse.** Every stack write is approved through this card, and the fingerprint covers the stack version and its author. A version someone starts after the card makes the approval stale.
  - Test: a version by `neuron_chat_editor` gives the warning, and approving after a new foreign version gives `stale`.
- **The card**, for each block preview on a shared area:
  - "{action} in the global area {name}", or "in the stack {name}" when the target is a stack directly.
  - A notice: "This changes every page that shows it: N pages, e.g. {up to 3 titles and paths}. It reaches the site when {this page | the stack} is published."
  - **Counted pages:**
    - Global area: active, non-system pages with an `Areas` row for that handle and `arIsGlobal = 1`, not page type defaults.
    - Stack: pages whose live version holds a Stack Display block for it.
  - The fingerprint adds the stack's newest version ID and its author.
- **The report.** The tool result carries `sharedArea: {name, kind, pages, examples, live}`, and `TurnChanges` names the stack draft on the "Changed:" line. No prompt rule (Rule 5).
- **Reads (recommended, not listed in the entry):** the model can't see a global area's blocks today, because `get_page_content` reads the page's own blocks.
  - `get_page_content` and `get_block_data` show a global area's blocks from the stack's newest version that the user may view. Each is marked `globalArea: {name, pages}`.
  - One integration test for each tool.
- **Moves.** A move from a global area to a page area copies the block into the page draft and removes it from the stack version, as edit mode does. A move the other way does the reverse. The card says both, with the page count. **Recommended: allow.**
- **Batch.** **Recommend:** `batch_update_page_content` keeps refusing global-area entries in P3.6a. The message points to `update_block_in_page_area`, so each shared change gets its own card and notice. `batch_update_content_headings` still never reaches them.
- **B-WRT-5 (b) → "met"** in `BEHAVIOUR_SPEC.md`, as the entry says.

## 3. Seed and scenarios
- **Seed:**
  - Two throwaway global areas, "Neuron Test Banner" and "Neuron Test Notice", each with one Content block. `neuron_content_editor` gets Edit Contents and Add Block on Banner only, as a page permission override on its stack page.

- **Runner:** new state checks:
  - `stack_draft: <name>`: an unapproved version holds the change, and the live version is unchanged;
  - `stack_unchanged: <name>`.
- **Scenario 39, "global-area edit through a page"** (current page `shared-a`): "Change the banner text to …", approve.
  - Expect: `stack_draft` Banner; `page_unchanged` shared-b; an approval card that names Banner with the page count.
  - Reply: says it shows on every page with the area and goes live when published (paraphrases accepted).
- **Scenario 40, "editor without stack permission refused":** "Change the notice text to …". Expect `stack_unchanged` Notice, no write succeeded, and a reply that names the permission or the administrator.

## 5. Risks
- **The page count is a floor.** Concrete writes a page's global `Areas` row the first time the page is shown, so pages that have never been viewed aren't counted. The card says "at least N".
- **Add through `BlockImportSave`** (P3.3-7) hasn't been tried on a stack version. The `SharedArea` tests cover it before the tools use it.
- **Stack permissions inherit from the home page** here, so editors are refused on real stacks. That's the safe default, and the seed's override gives scenario 39 its permission.
- **`SeedResetTest`** compares row counts, so the new stacks may need its expectations updated. That would be a change to a passing test, so I'd ask first.
