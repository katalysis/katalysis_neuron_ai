### 2.2 The `add_person` defect
`canWritePeople()` calls `$app->make('user')` (line 740). Concrete 9.5.5 binds no `'user'` key (searched `concrete/src/User`, `concrete/src/Application`, `concrete/config/app.php`), so the container treats it as a class name and throws "Target class [user] does not exist" under any SAPI, HTTP included. It's reached only when the user can't view the people dashboard page (an editor, not an admin), which is why it showed in the runner as `neuron_editor`. The fix is `$app->make(\Concrete\Core\User\User::class)`, what core `guarded()` does with `new User()`. It also affects `update_person`, `delete_person` and `delete_all_people`, which share `canWritePeople()`. All four stay disabled, so the model can't call them; the fix matters when they come back.

### 2.3 The registry and `ToolDefinition` today (core)
- `ToolDefinition` (P2.3) builds a `CallableTool` through `toNeuronTool()`. The handler gets the declared inputs as one array, `null` for a missing one. It adds no login check and no envelope.
- `ExternalToolkitRegistry::build()` takes only Neuron toolkits (`ToolkitInterface`). A toolkit becomes `FilteredToolkit::built()`, headed in the prompt by its class short name; `DisabledTools` then re-wraps it with `from()`, which gives v3's `# FilteredToolkit` / `Toolkit: KatalysisProEntitiesToolkit` lines.
- `ConcreteCmsAgent::tools()` runs every external toolkit through `ToolNameResolver` (external wins a clash), then `DisabledTools`, then the result scanner's `wrap()`, which wraps `CallableTool` handlers only. So `ToolDefinition`-built tools are covered by all three as soon as the registry accepts them.

## 4. Work

### 4.1 Core: the registry contract (this repo, PR into `integration/neuron4`)

```php
// In the package's on_start(), only when the core supports it:
if (method_exists(ExternalToolkitRegistry::class, 'registerToolDefinitions')) {
    ExternalToolkitRegistry::registerToolDefinitions(
        'katalysis_pro_entities',                          // provider key, as for registerToolkitFactory()
        static fn (): array => (new KatalysisProEntitiesToolkit())->definitions(),   // list<ToolDefinition>
        KatalysisProEntitiesToolkit::GUIDELINES,           // ?string, added to the prompt after the tool list
        'KatalysisProEntitiesToolkit'                      // label heading the guidelines (D4); defaults to the key
    );
}
```

- **`ExternalToolkitRegistry::registerToolDefinitions(string $key, callable $factory, ?string $guidelines = null, ?string $label = null)`:** stored in the same ordered list as the toolkit factories. The first registration for a key wins, as today.
- **`build()`:** a definitions provider is built inside the same try as a toolkit:
  - the factory runs once per agent
  - every item must be a `ToolDefinition`, or the whole provider is skipped with the reason
  - each definition goes through `toNeuronTool()` and then the login guard
  - the tools are offered as one `FilteredToolkit` with the guidelines, headed by the label (the existing constructor; no new `FilteredToolkit` API)
  - a factory or definition that throws is skipped, logged with secrets redacted, and listed on the settings page, the same as P2.2

  `registerToolkitFactory()` is unchanged: it's what the old `katalysis_pro` uses, and P3.10 retires it with a shim.
- **The login guard (core `guarded()`):** every definition's handler runs only for a registered user, as core `guarded()` does (`new User()`, `isRegistered()`), and throws "Authentication required: Please log in to use this tool." otherwise. Injectable for unit tests, like the registry's `$logger`.
- **The envelope (`ToolDefinition::toNeuronTool()`):**
  - a handler result that's an array with an `ok` key is returned as it is (every `katalysis_pro` result already is)
  - any other result becomes `{ok: true, data: <result>}`
  - an exception is left to the agent's tool error handler, which redacts and logs it

  So any future extension gets rule 4's envelope with no work.
- **Out of the contract for now:** group, tier, permission and approval (EXTENSIONS.md; P3.2, P3.5, P3.6, P3.10). `writes()` is recorded only, as now.
