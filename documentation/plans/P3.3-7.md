# P3.3-7 plan: Level 0 generic block adapter

Branch `task/P3.3-7-generic-block-adapter`, base `development`. A plan stop, because this is a design choice (the task's entry). The code was read on Concrete 9.5.5.

## 1. How the adapter learns a block type's fields (`BlockFields`, new)
- **Tables:** `$btExportTables`, or `[$btTable]` when that isn't set. This is the same list `BlockController::export()` uses. Columns come from the database (name, type, length, nullable). `bID` and a child table's `id` are left out.
- **Kinds:** the export lists give each column a kind:
  - `$btExportPageColumns`: page
  - `$btExportFileColumns`: file
  - `$btExportPageTypeColumns`: page type
  - `$btExportPageFeedColumns`: feed
  - `$btExportFileFolderColumns`: folder
  - `$btExportContentColumns`: html

  Every other column is text, number or flag, from its database type.
- **Child tables:** the export tables after the first. Their rows are ordered by `sortOrder` (or `displayOrder`) when the table has one, otherwise by `id`.
- **Not described.** A write refuses each of these with the reason. Reads still show what is stored, and nothing is guessed.
  - **(a) No `$btTable`.** The block stores nothing in a table. This also covers the `core_*` system blocks, which are already refused.
  - **(b) Undeclared side tables.** These are tables named after the block's table, with a `bID`, that the export doesn't list. Image's `btContentImageBreakpoints` is one; Concrete's own export loses it too. Reads list them as "other stored data, not described".
  - **(c) Child tables whose export or import the controller overrides with more than dropping `id`.** Gallery's nested display choices and Survey's results are examples. Their child rows can be read but not written. Accordion, Image Slider and FAQ only drop `id` (I read their controllers), so they go on a short list that is writable. Any other override is read-only until it's checked.
  - **(d) Undeclared references.** These are integer columns named `…ID` that no export list covers, such as `exFormID`. Level 0 can't tell what they point at, so they keep their stored value, and a change to one is refused.
- **Reads:** `get_block_data` lists each field with its kind and resolves references (a page to its path, a file to its name and URL), but only those the user may view. It shows the child rows of the declared tables. `SnapshotBuilder` uses the same declared tables instead of today's `LIKE '<table>%'` name match. One integration test covers the read tool.

## 2. Writes: import-mode `save()`, always into a draft (`BlockImportSave`, new)
- **Add:**
  1. Run the checks, before any draft.
  2. `getDraftOf($page)->getVersionToModify()->addBlock($bt, $area, $data, SaveMode::SAVE_MODE_IMPORT)`. This is the same call `AddBlockToPageCommandHandler` makes, which can't pass a save mode.
  3. Dispatch `on_block_add` as the handler does.
  4. Write the child rows.
- **Update:**
  1. Duplicate the block into the draft with `getBlockToEdit()`, as today. Its `duplicate()` copies the child rows.
  2. Build the controller with `saveMode = IMPORT`, then call `save()`. This is `Block::update()` with the mode set: `bDateModified` and the output-cache refresh, then `save()`. `Block::update()` takes no mode.
  3. Dispatch `on_block_edit`.
- **Import mode:** `save()` takes the columns as stored. Feature, Image and Page List skip Concrete's link picker and their form-only inputs, the same way a CIF import does.
- **Child rows** are written as `importAdditionalData()` writes them:
  - The table's rows for the draft's new `bID` are replaced. These are only the draft copy's rows, never the live block's.
  - The value's rows are used when the value names the table (key = table name). Otherwise the stored rows are kept.
  - Content columns go through `LinkAbstractor::translateTo()`, as the blocks' own `save()` does. This is idempotent; a test checks it.
  - Accordion and Image Slider `save()` delete their own entries first. The rows are written after `save()`, so that doesn't matter.
- **Failures:** any failure after the draft goes through `DraftCleanup`, as now (BF-3). `add_block_to_page_area`, `update_block_in_page_area` and `batch_update_page_content` share this path.

## 5. Risks
- **Reference columns (file, page, page type, feed, folder):**
  - Each new or changed ID must exist and be one the user may view. This uses the `ObjectPermissions` view checks, so it adds checks but changes no mechanism. Otherwise it's refused before any draft (red first).
  - Image Slider's `internalLinkCID` and Testimonial's `fID` are in the scenarios.
  - Undeclared references are never written (1d).
- **HTML and URL columns (B-T1-10):**
  - `UnsafeMarkup` runs on every string field, child rows included. Today it runs on the main record only.
  - Import mode skips Feature's `sanitizeURL()`. A **bare** `javascript:`, `data:` or `vbscript:` value in a plain column (`externalLink`, `linkURL`, `companyURL`) isn't caught today, because only attributes inside tags are checked. So a bare-URL check is added, red first, and applies to every string field in every mode.
- **Bypassing the two commands:** their only other work is the events, and those are dispatched here. A test checks that both events fire.
- **Data loss through undeclared side tables:** after `save()`, the rows of undeclared side tables for the draft block are compared with the copy. If `save()` removed rows the call didn't ask about, the write fails, the draft is discarded, and the refusal names the table. Image is the one block with a hand-written keep.
- **Package blocks:** Block Designer-style blocks (one table plus an `…Entries` table, no export override) get full Level 0. A package block with its own non-column `save()` inputs isn't known; its inputs are refused as unknown fields, which is clear but narrower than "anything goes".
