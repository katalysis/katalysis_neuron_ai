### 2.5 Scanner in our own tool class, middleware for the rest
- `src/Tools/Support/CallableTool.php` (new, `@internal`): written from the spike's design (findings 3.1), not copied: name and description in the constructor, the handler as a closure, variadic `__invoke()`, `invokeParameters()` returning `[]`, strict inputs in `execute()` (StrictInputTool's rule, for every tool built with it), `wrapHandler()`.
- `src/Security/ToolResultScanner.php`:
  - `wrapTool()` wraps `CallableTool` through `wrapHandler()`; no `Closure::bind` on Neuron internals; any other tool is left alone and `isWrapped()` returns false for it.
  - `wrapToolkit()` builds the toolkit's tools once, wraps them, and returns a toolkit with that fixed list (`FilteredToolkit::built()`, below). No more `with()`: v4 keeps one `with()` callback per class, so anything else using it would replace the scanner's (findings 3.2). This takes that item from P2.3.
  - `resultMiddleware()`: an `AgentMiddleware` for `ToolNode` that scans every tool result the wrapper did not inspect. The wrapper records what it inspected (tool call, result hash); the middleware checks that record, not `isWrapped()`. So a wrap that silently fails is still covered.
  - Known limit (findings 4), unchanged and not reachable today: in streaming mode raw chunks reach the browser before the middleware runs. The panel doesn't stream.
- `src/Tools/FilteredToolkit.php`: a second named constructor, `built()`, for a fixed list with the original guidelines **verbatim** (no "Toolkit: X" line), so the prompt is unchanged. `from()` keeps its behaviour.
- `src/ConcreteCmsAgent.php`:
  - constructor: `addMiddleware(ToolNode::class, $this->toolResultScanner()->resultMiddleware())`;
  - the core toolkit list moves into `protected function coreToolkits(): array` (a seam for the integration test; same list, same order);
  - `tools()` uses the registry's build for this agent (2.6).
  - Nothing else in the agent changes in P2.2 (history, instructions, error path: P2.4–P2.6).

### 2.6 Skip and log a failing external toolkit
- `src/Tools/ExternalToolkitRegistry.php`:
  - `build(?callable $logger = null): ExternalToolkitBuild`: for each factory, inside one try per toolkit, call `tools()` **once**, and keep the result as `FilteredToolkit::built($toolkit, $tools)`, so nothing calls `tools()` on the original again (an MCP toolkit would reconnect). A factory or toolkit that throws is skipped: logged as a warning, and recorded as (provider key, toolkit class, message through `SecretRedactor`).
  - `getExternalToolkits()` stays, as `build()->toolkits()`, for any caller outside the agent.
- `src/Tools/ExternalToolkitBuild.php` (new, small value object): `toolkits()`, `skipped()`.
- `ConcreteCmsAgent` builds once per agent instance and reuses it if Neuron asks for the tools again.
- Settings page (`controllers/single_page/dashboard/system/ai/neuron_ai.php`, `single_pages/dashboard/system/ai/neuron_ai.php`): `view()` runs the same `build()` and shows a warning listing each skipped toolkit (package key, class, reason) to users who can configure. **Choice made:** a live dry build on page view, not a stored record of the last chat turn. It is always current and writes nothing (no `Config` row per turn, no leak-check noise). Cost: external toolkits are constructed on each settings view; none connects to anything today (6.4).
- On the dev site this shows `katalysis_pro`'s toolkit as skipped ("Cannot instantiate abstract class NeuronAI\Tools\Tool") until P2.8.
