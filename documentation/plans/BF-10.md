# BF-10 plan: the assistant sees what the editor sees

Status: **draft, waiting for approval (Glyn).** Significant task: it changes what read tools return and their descriptions (what the model sees), the scenario fixture (the seed) and the scenario runner. Branch `task/BF-10-read-newest-version` from `development`, PR into `development`.

## 1. Goal
Every read tool shows, by default, the page's newest version (the one editors see and the write tools change), says which version it shows, and says when the published version differs, so a block ID the model reads is one it can write to first time.

## 2. Why (from BF-7's browser check 6)
The write tools change the newest version (`PageDraft::of()`), and Concrete shows editors the newest version. `get_page_content` reads the published version by default and says so in its description. In check 6 the model read the published version, wrote with a block ID that the user's own hand edit (another tab, edit mode) had replaced, and got "Block 31610 not found". BF-7 made that error specific (`BlockNotFound`) so the retry works; BF-10 removes the cause, so there is no failed first call.

### 3.1 Values and compatibility
- `version` takes `"newest"` (default) or `"published"`. The old `"recent"` and `"active"` stay accepted as the same values, so existing calls and tests (`GetPageContentTest`, `ToolResultScanningTest`, `EscapedContentTest`) keep working unchanged. Anything else is refused with the two valid values.
- `includeInactive` is replaced on the three block-list tools (unknown inputs are refused since P2.3, so a call that still sends it gets that refusal, naming `version`). Each change is listed in `ToolBaseline::DELIBERATE_CHANGES` (§6).
- **Permissions.** Reading an unpublished version needs `view_page_versions`, as now. When the user lacks it:
  - the **default** read falls back to the published version and says so (`version.shows: "published"`, with the reason), instead of failing;
  - an explicit `"newest"` is refused, as `"recent"` is today.

  The seeded `neuron_editor` and `neuron_chat_editor` have `view_page_versions`, so the scenarios read the newest version.
- **A page that was never published** (made by `create_page`): the default read works (today `get_page_content` reads `ACTIVE`, which has no approved version); `"published"` says there is no published version yet and that the default shows the newest.

### 3.2 One shared helper

The four PagesToolkit reads and the prompt snapshot use it. The block-list tools use its version-ID lookup (`newest` = `MAX(cvID)` per page, as `BlockNotFound` already does).

## 4. What the model sees

### 4.1 Page reads: a `version` block in every result
`get_page`, `get_page_content`, `get_page_blocks` and `get_current_page_context` return:

```json
"version": {
  "shows": "newest",
  "versionID": 12,
  "status": "unpublished",
  "publishedVersionID": 11,
  "summary": "Newest version (12, unpublished, saved by neuron_editor): what editors see and what the write tools change. Visitors see version 11 until someone publishes. Use block IDs from this version."
}
```

- **Newest and published are the same:** `"status": "published"`, and the summary is one short line: "Newest version (11), which is also the published version."
- **Published asked for, and the newest differs:** `"shows": "published"`, plus `"newestVersionID": 12`, and the summary: "Published version (11): what visitors see. The newest version (12, unpublished) has changes not shown here; the write tools change that version, and block IDs here may not be in it."
- **Fallback for lack of permission:** `"shows": "published"` and the summary says the user can't view unpublished versions of this page, so this is the published version.
- `get_page_content`'s existing `version` keys (`cvID`, `isActive`, `versionHandle`) stay, so its current tests keep passing; `versionHandle` reports `RECENT` or `ACTIVE` as now.

### 4.2 Should a read mention that unpublished changes exist? **Yes, only when they do.**
- It is a fact about the page, in the tool result, not a prompt rule (CLAUDE.md rule 5).
- It lets the model answer "what's live?" truthfully (B-TRU-8) and explains a later difference between what it read and what visitors see.
- When the versions are the same it adds one short line, nothing alarming.
- The author name is the one `BlockNotFound` already shows (BF-7); it tells the user their own edit-mode change is in that version.

### 4.3 Block reads
`get_block_data` and `get_block_controller_data` add a version line:
- **The block is in the newest version:** "Version: in the newest version (12, unpublished)" (or "(11, published)").
- **It is not** (an ID read earlier, or from the published version): the read still returns the block's data, and says, in the words `BlockNotFound` uses, that it is in the published version (or version N) and not in the newest version, which the write tools change. It gives the ID the newest version has at the same position. To share the lookup, `BlockNotFound` gets a `locate()` method that `explain()` and the block reads both use; its messages keep their wording, except `get_page_blocks (version "recent")` becomes `get_page_blocks (it reads the newest version)`. `StaleBlockIDTest` asserts only `get_page_blocks`, so it is unaffected.

The block-list tools' tables keep their ✅/📝 column and say which version they list in their heading line.

## 6. The edit-mode fixture

### 6.1 Where CR LF and `&nbsp;` come from
They are made in the browser, not on the server: the rich-text editor writes `&nbsp;` (for a double space, a trailing space or an empty paragraph) and its own line breaks, and the browser's form submission turns every line break into CR LF. Concrete's server path then stores what was posted (`GetBlockToEditTrait::getBlockToEdit()`, then the content controller's `save()`). So no server-side script can produce "what edit mode saves" by itself: the bytes have to come from a real browser save once.
